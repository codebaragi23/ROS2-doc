# B2. 좌표계와 로컬라이제이션 기반

> Nav2 내비게이션 (Part B) 시리즈
> 이전 문서: B1. Nav2 아키텍처 개요

## 1. 개요

Nav2가 정확히 동작하려면 `map`, `odom`, `base_footprint` 세 좌표계의 관계가 항상 살아 있어야 한다. 이 문서는 이 관계가 각각 누구에 의해 채워지는지, 그리고 이 프로젝트가 Nav2 표준 예제(AMCL 기반)와 어떻게 다른 구조인지 정리한다.

## 2. 핵심 개념: TF 트리와 책임 분담

```text
map ──(로컬라이제이션 시스템이 채움)──▶ odom ──(EKF/오도메트리가 채움)──▶ base_footprint
```

- **`odom → base_footprint`**: 바퀴 인코더, IMU를 융합한 EKF(`ekf_filter_node`)가 연속적으로 발행한다. 이 값은 항상 부드럽게 이어지지만, 시간이 지날수록 실제 위치에서 서서히 벗어나는(drift) 특성이 있다.
- **`map → odom`**: 지도를 기준으로 한 절대 위치 보정값이다. 이 TF를 실제로 누가 발행하는지는 로봇 구성에 따라 다르다 — Nav2 표준 예제에서는 보통 AMCL이 이 역할을 맡지만, RTAB-Map처럼 시각 정보 기반 로컬라이제이션을 쓰는 구성도 가능하다.

이 구분이 이 시리즈 전체에서 가장 중요한 개념이다: **Nav2 자체는 `map→odom`을 누가 채우는지 신경 쓰지 않는다.** `bt_navigator`, `planner_server`, `controller_server` 모두 이 TF가 최신 상태로 존재한다고만 가정하고 동작한다. 즉 로컬라이제이션 품질 문제는 Nav2 파라미터가 아니라 **`map→odom`을 채우는 로컬라이제이션 시스템 쪽에서 원인을 찾아야 한다.**

**핵심 대비 — drift와 jump는 서로 다른 현상이다**

두 TF는 오차가 나타나는 방식이 정반대이며, 이 대비가 Part B·C 전체 진단 논리의 축이다.

> **`odom`은 drift하지만 jump하지 않고, `map`은 jump하지만 drift하지 않는다.**

- **drift(드리프트)**: 오차가 **연속적으로 서서히 누적**되는 것. `odom → base_footprint`가 그렇다. 매 순간은 부드럽게 이어지지만 10분 뒤엔 실제 위치에서 수 미터 벗어나 있을 수 있다.
- **jump(점프)**: 위치가 **순간적으로 불연속하게 튀는** 것. `map → odom`이 그렇다. 로컬라이제이션이 "아, 내 위치가 틀렸구나" 하고 보정하는 순간 값이 확 바뀐다.

이는 [REP105](https://www.ros.org/reps/rep-0105.html) 표준이 의도한 설계다 — 부드러움이 필요한 계층(로컬 제어, local costmap)은 `odom`을 쓰고, 전역 정확성이 필요한 계층(경로 계획)은 `map`을 쓴다. C4에서 다룰 Pose Jump 문제는 이 설계의 필연적 부작용이지 버그가 아니다.

## 2-1. 위치 추정의 불확실성 — 공분산, 필터, 파티클

Part C 전체가 "지금 위치 추정을 믿을 수 있는가"를 수치로 판단하는 내용이므로, 그 수치들이 무엇인지 여기서 먼저 정리한다.

**추정에는 항상 불확실성이 따른다**

로봇이 "나는 (3.2m, 1.5m)에 있다"고 말할 때, 이는 정확히 그 점이라는 뜻이 아니라 **"대략 그 근처"**라는 뜻이다. 얼마나 "대략"인지를 나타내는 값이 **공분산(covariance)**이다.

- 공분산이 **작다** = "정확히 여기"라고 자신 있는 상태. 추정 위치를 타원으로 그리면 아주 작은 점에 가깝다.
- 공분산이 **크다** = "이 근방 어딘가"라고 자신 없는 상태. 타원이 넓게 퍼진다.

실제로는 x, y, yaw 등 여러 값에 대한 행렬 형태지만, 실무에서는 보통 **대각 성분(각 축의 불확실성)이 임계값을 넘는지**를 보고 "위치를 잃었다"고 판단한다. Part C의 여러 트리거가 이 값을 기준으로 삼는다.

**필터란 — 두 개의 불확실한 정보를 합쳐 더 확실하게 만드는 것**

`odom → base_footprint`를 만드는 `ekf_filter_node`의 EKF(Extended Kalman Filter, 확장 칼만 필터)가 하는 일이 바로 이것이다.

- 바퀴 인코더도 부정확하고(미끄러지면 틀림), IMU도 부정확하다(시간이 지나면 표류). 그런데 **두 정보를 각각의 신뢰도로 가중평균하면 어느 하나보다 정확한 값**이 나온다 — 자신 있는 쪽 말을 더 크게 반영하는 방식이다.
- 필터는 이 과정을 매 순간 반복한다: **예측**(직전 상태로부터 지금 위치를 추측) → **보정**(새 센서값이 들어오면 그쪽으로 끌어당김). 이때 불확실성이 낮다고 표시된 측정값일수록 더 세게 끌어당긴다.
- "확장(Extended)"이 붙은 이유는, 원래 칼만 필터가 직선적인 관계만 다룰 수 있는데 실제 회전·이동은 휘어 있어서 **매번 현재 추정값 근처에서 직선으로 근사해** 쓰기 때문이다.

**파티클 필터 — AMCL이 쓰는 다른 방식**

같은 문제를 완전히 다르게 푸는 방법도 있다. AMCL(Adaptive Monte Carlo Localization)이 쓰는 **파티클 필터**다.

1. 로봇이 있을 법한 위치 후보 수천 개를 지도 위에 점(파티클)으로 뿌린다.
2. LiDAR 스캔이 들어오면, 각 후보 위치에서 봤을 때 지도와 얼마나 잘 맞는지 채점해 **가중치**를 준다.
3. 점수가 높은 후보 주변에 점들을 다시 뿌리고, 낮은 후보는 버린다.
4. 반복하면 점들이 한 곳으로 **수렴**하고, 그 지점이 추정 위치가 된다.

이 방식의 장점은 **"여기 아니면 저기"처럼 후보가 여러 곳으로 갈리는 상황도 자연스럽게 표현**할 수 있다는 것이다. 점들이 넓게 퍼져 있으면 전역 탐색 중, 한 곳에 모여 있으면 추적이 안정된 상태다 — C1에서 다룰 "1단계(전역 탐색) vs 2단계(추적)" 구분이 파티클 필터에서는 이렇게 시각적으로 드러난다.

## 3. 이 프로젝트에서의 적용 (Yahboom X3): RTAB-Map localization vs AMCL

이 프로젝트에서는 AMCL 대신 **RTAB-Map localization이 `map→odom` TF를 발행한다.** 즉 위 2장의 일반 구조에서 "로컬라이제이션 시스템" 자리에 RTAB-Map이 들어간 것이며, 로컬라이제이션 품질 문제의 원인은 RTAB-Map 쪽에서 찾아야 한다 — 구체적인 진단 절차는 C1~C6(Relocalization 심화)에서 다룬다.

| 구분 | AMCL (Nav2 표준) | RTAB-Map Localization (이 프로젝트) |
|---|---|---|
| 입력 | 2D LiDAR 스캔 + 정적 지도 | RGB-D 이미지 + LiDAR 스캔 + RTAB-Map DB |
| 알고리즘 | 파티클 필터(Monte Carlo Localization) | Appearance-based loop closure + 그래프 최적화 |
| 초기 위치 지정 | `/initialpose` 토픽, `set_initial_pose` 서비스 | `/rtabmap/initialpose` 토픽 (유사하지만 별도 메커니즘) |
| Kidnapped 대응 | `reinitialize_global_localization` 서비스(공식 제공) | 공식 서비스 없음 — loop closure 재탐지에 의존 |
| 지도 형태 | 2D occupancy grid만 필요 | RTAB-Map DB(그래프+특징점) 필요 |

이 표가 이 시리즈의 핵심 전제다: **Nav2가 공식 문서에서 설명하는 relocalization 절차(AMCL의 `reinitialize_global_localization`)는 이 프로젝트에 그대로 적용되지 않는다.** Part C에서 다루는 relocalization 전략은 전부 RTAB-Map 레이어에서 별도로 설계된 것이다.

로컬라이제이션 모드 진입은 RTAB-Map의 `Mem/IncrementalMemory` 파라미터로 결정된다.

```yaml
# 매핑 모드 (지도를 새로 만들며 계속 확장)
Mem/IncrementalMemory: true

# 로컬라이제이션 모드 (기존 지도 안에서 내 위치만 찾음, 지도는 더 이상 확장하지 않음)
Mem/IncrementalMemory: false
```

## 3-1. 실습: drift와 jump를 직접 목격하기

2장에서 "**`odom`은 drift하지만 jump하지 않고, `map`은 jump하지만 drift하지 않는다**"고 했다. 이 문장이 Part C 전체의 축이므로, **말로 이해하는 대신 화면에서 직접 보는 것**이 훨씬 확실하다.

### 실습 목표

`map → odom` TF가 평소에는 거의 고정되어 있다가, loop closure가 성공하는 순간 **불연속하게 튀는 것**을 눈으로 확인한다.

### 준비 사항

* A2 실습에서 만든 `rtabmap.db`
* 로컬라이제이션 모드로 실행 가능한 상태

### 실행

```bash
# 1) 로컬라이제이션 모드로 실행 (지도를 새로 만들지 않고 기존 지도에서 위치만 찾음)
ros2 launch rtabmap_launch rtabmap.launch.py \
  localization:=true \
  rgb_topic:=/camera/color/image_raw \
  depth_topic:=/camera/depth/image_rect_raw \
  camera_info_topic:=/camera/color/camera_info \
  frame_id:=base_link
```

```bash
# 2) 별도 터미널: map→odom 보정값을 실시간으로 관찰
ros2 run tf2_ros tf2_echo map odom
```

```bash
# 3) 또 다른 터미널: 비교용으로 odom→base_link도 함께 관찰
ros2 run tf2_ros tf2_echo odom base_link
```

이 상태로 로봇을 **지도에 없는 방향으로 한참 이동시켰다가, 지도에 있는 익숙한 장소로 되돌아온다.**

### 확인 — 두 터미널의 숫자가 어떻게 다른가

| 터미널 | 로봇이 움직일 때 | loop closure가 성공하는 순간 |
|---|---|---|
| `map → odom` (2번) | **거의 변하지 않음** — 값이 멈춰 있는 것처럼 보인다 | **숫자가 갑자기 확 바뀐다**(jump) |
| `odom → base_link` (3번) | **계속 부드럽게 변함** — 로봇 움직임을 그대로 따라감 | 특별한 변화 없음, 계속 부드럽게 이어짐 |

### 예상 결과

- **2번 터미널의 값이 튀는 그 순간**이 바로 C4에서 다룰 Pose Jump가 발생하는 시점이다. RViz를 함께 켜두면 로봇 아이콘이 순간이동하는 것을 볼 수 있다.
- **3번 터미널은 그 순간에도 부드럽다** — 이것이 "local costmap이나 컨트롤러가 `odom` 기준으로 동작하는 이유"다. 그 계층은 jump에 영향받지 않아야 하기 때문이다(B3).
- 로봇을 오래 주행시킬수록 실제 위치와 `odom` 추정치가 서서히 벌어지는데(drift), 그 누적분을 loop closure가 한 번에 보정하므로 **오래 돌수록 jump 폭도 커진다.**

> **이 실습의 의미**: C4(Pose Jump 제어)는 "왜 점프가 생기고 어떻게 완화하는가"를 다루는데, 점프를 한 번도 못 본 상태로 읽으면 추상적인 이야기로만 남는다. 여기서 직접 목격해두면 Part C 전체가 구체적으로 읽힌다.

## 4. 관련 파라미터

**Nav2 공통 (로컬라이제이션 시스템 종류와 무관)**

| 파라미터/설정 | 위치 | 역할 |
|---|---|---|
| `robot_base_frame: base_footprint` | Nav2 전역 | Nav2가 로봇 위치로 취급하는 좌표계 — URDF/TF/costmap/EKF 출력과 일치해야 함 |
| `global_frame: map` (bt_navigator) | Nav2 전역 | 목표와 전역 경로의 기준 |
| `global_frame: odom` (costmap 등 로컬 요소) | 로컬 요소 | 연속적인 odom 기준으로 동작해야 하는 부분(local costmap, recovery)의 기준 |

**이 프로젝트(RTAB-Map localization) 전용**

| 파라미터/설정 | 위치 | 역할 |
|---|---|---|
| `Mem/IncrementalMemory` | RTAB-Map | true=매핑, false=로컬라이제이션 |
| `RGBD/SavedLocalizationIgnored` | RTAB-Map | 새 loop closure 감지 시 저장된 localization을 무시하고 강제 relocalization할지 여부 |

## 5. 진단 관점

- 로봇이 지도 위에서 위치가 튄다면(jump) → `map→odom` 문제이므로 RTAB-Map localization confidence, loop closure 로그를 먼저 본다. `odom→base_footprint`는 EKF 문제이므로 IMU/휠 오도메트리를 본다. **두 계층을 구분해서 진단하는 것이 핵심**이다.
- `base_footprint`와 `base_link`를 혼동하지 않는다 — `base_link`는 로봇 몸체 실제 중심(높이 포함), `base_footprint`는 바닥 투영(z=0)이다. Nav2의 2D 내비게이션은 대부분 `base_footprint` 기준으로 계산한다.
