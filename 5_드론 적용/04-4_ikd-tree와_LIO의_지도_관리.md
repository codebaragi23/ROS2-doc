## 1. 개요

[[04-3_FAST-LIO2_알고리즘_구조|04-3]] 6장에서 본 것처럼, FAST-LIO2는 **매 프레임 수천 번의 최근접 검색**을 한다. 점 하나마다 "지도에서 가장 가까운 5점"을 찾아야 하기 때문이다.

그러려면 지도를 검색에 최적화된 자료구조로 들고 있어야 하는데, **문제는 그 지도가 매 프레임 바뀐다**는 것이다. 이 문서는 그 문제를 푸는 ikd-tree와, 거기서 파생되는 실무적으로 아주 중요한 결론 하나를 다룬다.

> **그 결론을 미리 적으면 이렇다**: **방 안에 가만히 서 있으면 FAST-LIO2의 지도는 더 이상 커지지 않는다.** 이 한 문장이 [[08_사례연구_정지_상태_발산|둠둠 08]] 전체를 이해하는 열쇠다.

## 2. 핵심 개념: 왜 평범한 kd-tree로는 안 되는가

k-d tree는 다차원 공간에서 최근접 검색을 빠르게 하는 표준 자료구조다. 하지만 **정적인 데이터**를 전제로 만들어졌다.

```
[일반 k-d tree]
  점을 추가/삭제하면 트리가 한쪽으로 치우쳐(unbalanced) 검색 성능이 무너진다
  → 균형을 되찾으려면 전체를 다시 짓는다(rebuild)
  → 매 프레임 전체 재구축은 불가능

[ikd-tree = incremental k-d tree]
  · 점 추가/삭제를 트리를 갈아엎지 않고 처리
  · 균형이 깨진 서브트리만 골라서 부분 재구축
  · 큰 서브트리 재구축은 별도 스레드로 넘겨 메인 루프를 막지 않는다
  · 삭제는 lazy delete(지웠다고 표시만 하고 나중에 정리)
```

효과는 극적이다. 논문 실측으로 증분 갱신 평균 **0.23 ms** vs 정적 k-d tree 재구축 **5.71 ms**(약 25배), LIO 전체에서 정적 트리 대비 **약 4%**의 시간만 쓴다.

> **[[04-3_FAST-LIO2_알고리즘_구조|04-3]] 8장의 "특징점 추출을 버릴 수 있었던 이유"의 나머지 절반이 이것이다.** 칼만 이득 재정식화가 "점이 많아도 필터가 안 터진다"를 보장했다면, ikd-tree는 "점이 많아도 **검색**이 안 터진다"를 보장한다. 둘 중 하나만 없어도 direct 방식은 성립하지 않는다.

### 2.1 균형을 언제 다시 잡는가

두 가지 기준 중 하나라도 깨지면 **그 서브트리만** 재구축한다.

| 기준 | 뜻 | 기본값 |
|---|---|---|
| α-balanced | 좌/우 서브트리 어느 쪽도 너무 크면 안 된다 | 0.6 |
| α-deleted | 삭제 표시된 노드가 너무 많이 쌓이면 안 된다 | 0.5 |

**전체가 아니라 문제가 생긴 부분만 고친다** — 이것이 "incremental"의 실질이다.

### 2.2 그리고 ikd-tree는 자기 스레드를 돌린다

재구축 대상 서브트리가 일정 크기(기본 1,500 노드)를 넘으면 **별도 스레드로 넘긴다.** 그 스레드는 이렇게 동작한다.

```
[rebuild 스레드]
  1. 대상 서브트리의 "갱신"을 잠근다 (검색은 계속 허용)
  2. 유효한 점들을 평탄화해 배열로 뽑는다
  3. 잠금 해제 → 그 사이 들어온 갱신은 별도 큐(operation logger)에 기록됨
  4. 균형 잡힌 새 서브트리를 만든다
  5. 큐에 쌓인 갱신을 새 트리에 재생(replay)
  6. 아주 짧게 전체를 잠그고 서브트리 포인터를 교체, 옛 메모리 해제
```

**이 사실을 기억해 둔다.** 지금은 "ikd-Tree는 우리가 모르는 사이에 자기 스레드에서 트리를 재구축하고 있다"만 알면 된다. [[09_사례연구_28km_발산과_ROS2_포팅_회귀|둠둠 09]]에서 이 스레드의 존재를 몰랐던 대가로 **28km 발산**이 일어난다.

> **일반화**: 라이브러리가 내부에서 스레드를 돌리면, **당신의 "우리는 싱글 스레드니까 안전하다"는 가정이 무효가 된다.** 라이브러리를 쓸 때 `pthread_create`/`std::thread`를 grep해 보는 것은 몇 초짜리 습관이지만 사고를 막는다.

## 3. 핵심 개념: 지도가 무한히 커지지 않는 두 장치

ikd-tree에는 크기를 스스로 관리하는 장치가 둘 있다. **둘 다 아는 것이 중요하다** — 뒤에서 이 장치가 **없는** 버퍼가 등장하기 때문이다.

### (A) 삽입 시 격자 중복 제거

새 점을 넣기 전에, 그 점이 속한 격자 칸(`filter_size_map`, 기본 0.5 m)에 **이미 더 중심에 가까운 점이 있으면 넣지 않는다.**

```
  격자 한 칸(0.5m)
  ┌─────────────┐
  │      ● 기존점 │   새 점이 들어와도, 기존점이 칸 중심에
  │       ·  ○   │   더 가까우면 새 점은 버려진다
  └─────────────┘
```

> **결과: 같은 벽을 3,500번 다시 봐도 점이 늘지 않는다.**

### (B) 공간 정리(트리밍)

로봇이 이동해 지도 상자의 경계에 가까워지면, 상자를 진행 방향으로 옮기고 **뒤에 남는 영역을 트리에서 통째로 삭제**한다(box-wise delete).

기본 설정(`cube_side_length: 1000.0`, `det_range: 100.0`)에서:

```
상자 반경 = 1000/2 = 500 m
발동 거리 = 1.5 × 100 = 150 m
→ 시작점에서 약 350 m 이상 가야 비로소 잘라내기 시작한다
```

**실내에서는 평생 발동하지 않는다.** 그래도 (A)가 있어 크기가 폭주하지 않으므로 무해하다.

> **주의**: `cube_side_length`를 `det_range`에 비해 너무 작게 잡으면 트리밍 로직이 의도대로 동작하지 않을 수 있다. 공식 기본값의 비율이 **10배**(1000 : 100)이니, 줄일 이유가 없다면 건드리지 않는 편이 안전하다.

### 3.1 결론: 크기는 "시간"이 아니라 "공간"에 비례한다

```
     ikd-tree 크기
        │
        │      ┌──────────────  ← 방을 다 훑고 나면 평평해진다
        │     ╱
        │    ╱   (새로 보는 공간이 있을 때만 큰다)
        │   ╱
        └──────────────────────► 시간
```

**가만히 있으면 새 기하 정보가 없으므로 (A)의 중복 제거에 전부 걸린다 — 트리가 더 이상 안 커진다.** 이것이 정상이고 의도된 동작이다.

## 4. 핵심 개념: 이름이 비슷한 세 개의 노브

거의 모든 사람이 헷갈린다. **적용 대상이 완전히 다르다.**

```
   원시 스캔
        │
        │ ① point_filter_num       "N개당 1개만 통과"  (개수 기반)
        ▼
   솎인 스캔
        │
        │ ② filter_size_surf       "이번 스캔"을 격자로 솎기 (공간 기반)
        ▼
   매칭에 쓰는 점 ─────► ESIKF 매칭 (04-3)
        │
        │ ③ filter_size_map        "지도(ikd-tree)"의 격자 해상도
        ▼
   ikd-tree에 저장
```

| | 적용 대상 | 작게 하면 |
|---|---|---|
| `point_filter_num` | 들어오는 원시 점 | 쓰는 점이 늘어 정밀 ↑, CPU ↑ |
| `filter_size_surf` | **이번 스캔**(입력) | 매칭 정밀 ↑, 최근접 검색 호출 ↑ → CPU ↑ |
| `filter_size_map` | **저장된 지도**(ikd-tree) | 지도 정밀 ↑, 트리 크기 ↑ → 탐색 CPU ↑ |

### 4.1 기본값 0.5는 Mid-360용 튜닝값이 아니다

공식 `mid360.yaml`의 `filter_size_surf: 0.5`, `filter_size_map: 0.5`는 **다른 센서(avia) 설정에서 그대로 온 값**이다. 실내에서는 큰 편이다.

- **저장소 유지보수자 권고**: 실내 드리프트 보고(issue #61)에 대해 **둘 다 0.2로** 낮춰볼 것을 권했고, 보고자가 개선을 확인했다. 다른 이슈에서는 실내에 0.05 / 0.15와 `point_filter_num` 5~10을 제시한 사례도 있다.
- **이 프로젝트 실측**(정지 상태 재생 A/B): `0.2` + `point_filter_num: 2` 조합에서 정지 누적오차 최대 **4.9 cm → 2.7 cm**. 단 CPU는 0.19 → 0.28로 증가.

> **중요**: `filter_size_surf`만 줄이고 `point_filter_num`을 그대로 두면 **애초에 들어오는 점이 부족해 효과가 안 난다.** ①이 상류에서 이미 솎아버렸기 때문이다 — **둘은 같이 움직여야 한다.** 파라미터 표만 보고 하나씩 만지면 이런 상류-하류 관계를 놓친다.

## 5. 핵심 개념: 두 개의 "지도" — 이 문서에서 가장 중요한 절

FAST-LIO 안에는 **"지도"라는 말이 가리키는 것이 두 개** 있고, 성격이 완전히 다르다.

```
┌─────────────────────────────────────────────────────────────────┐
│ (A) 알고리즘이 실제로 쓰는 지도 —  ikd-tree                       │
│                                                                 │
│  · 새 스캔을 "어디에 맞출지" 비교하는 기준. 없으면 위치추정 불가    │
│  · 삽입 시 격자 중복 제거 (3장 A)                                │
│  · 멀리 이동하면 뒤 영역 잘라냄 (3장 B)                          │
│  ⇒ 크기가 "공간"에 비례. 방 안에 가만히 있으면 안 커진다          │
└─────────────────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────────────────┐
│ (B) 사람이 보는 지도 — 시각화 / 저장용 버퍼                       │
│                                                                 │
│  · RViz에 띄우거나 PCD로 내보내는 용도                            │
│  · 위치 추정에는 전혀 쓰이지 않는다. 없어도 알고리즘은 잘 돈다      │
└─────────────────────────────────────────────────────────────────┘
```

**두 지도를 구분하지 못하면 관측을 잘못 읽는다.** "지도가 커진다"가 (A)를 뜻하면 정상(공간에 비례)이고, (B)를 뜻하면 문제일 수 있다. [[08_사례연구_정지_상태_발산|둠둠 08]]의 사고가 정확히 이 혼동 위에서 며칠을 잡아먹었다.

### 5.1 발행되는 토픽 — 누가 누적하는가

| Topic | 좌표계 | **노드가 누적하나** | 내용 |
|---|---|---|---|
| `/cloud_registered` | world | **아니오** | 현재 스캔만 world로 변환 |
| `/cloud_registered_body` | body | 아니오 | 같은 스캔을 로봇 중심 좌표계로 |
| `/cloud_effected` | world | 아니오 | ESIKF가 실제로 채택한 점만([[04-3_FAST-LIO2_알고리즘_구조\|04-3]] 6.2절) |
| `/Laser_map` | world | **예** | 노드 내부 버퍼에 계속 더한다 — **(B)가 이것이다** |
| `/Odometry` | body→world | - | 추정 pose |
| `/path` | world | 예 | 궤적 선 |

### 5.2 흔한 오해 둘

**오해 1 — "RViz에서 지도가 쌓이니까 노드가 누적하는 것이다"**

아니다. RViz 설정의 **Decay Time**(예: 30초)이 지난 메시지를 화면에 남기는 것이다. **누적이 토픽이 아니라 보는 쪽에서 일어난다.** [[08_rqt_rviz2_활용|ROS2 기초 08]]에서 다룬 RViz Display 설정이 관측 해석을 바꾸는 사례다.

**오해 2 — 좌표계 이름**

FAST-LIO2의 world frame 이름은 **`camera_init`**이다(LiDAR인데 `camera`인 것은 LOAM 계보의 유산이다). 저장한 PCD를 다른 도구로 다시 발행하면 기본 frame이 달라 **라이브 데이터와 frame이 어긋나** RViz에서 아무것도 안 보인다. 이 프로젝트도 실제로 겪었고, `Fixed Frame`을 통일해 해결했다. [[07_TF2_기초|ROS2 기초 07]]의 "frame_id가 TF 트리 이름과 일치해야 한다"가 그대로 적용된다.

## 6. 진단 관점

| 증상 | 확인 순서 |
|---|---|
| 지도(ikd-tree)가 계속 커진다 | **이동 중이면 정상**(공간에 비례). 정지 중인데 커진다면 (A)가 아니라 (B)를 보고 있는 것이다(5장) |
| 시간이 갈수록 느려지고 결국 죽는다 | **(B) 버퍼의 무한 누적을 의심한다** — [[08_사례연구_정지_상태_발산\|둠둠 08]] |
| `filter_size_surf`를 줄였는데 정밀도가 그대로 | `point_filter_num`이 상류에서 이미 솎고 있다(4.1절). 둘을 같이 조정한다 |
| RViz에 점이 하나도 안 보임 | `Fixed Frame`이 `camera_init`인지 확인(5.2절) |
| 저장한 PCD를 다시 띄웠더니 안 보임 | 재발행 도구의 기본 frame이 다른 것(5.2절) |
| 실내인데 드리프트가 큼 | `filter_size_surf`/`filter_size_map`을 0.2 수준으로, `point_filter_num`을 함께 낮춰본다(4.1절). CPU 여유를 반드시 같이 측정한다 |
| 메모리가 계속 는다 | ikd-tree는 lazy delete라 "삭제 표시"된 노드가 재구축 전까지 남는다. 트리 크기 ≠ 유효 점 수라는 점을 감안하고, 그래도 선형 증가면 (B)를 의심한다 |

## 7. 이해도 점검

1. 방 안에 센서를 놓고 30분간 가만히 두었다. ikd-tree의 크기는 어떻게 되는가?
2. 일반 k-d tree 대신 ikd-tree가 필요한 이유를 한 문장으로 설명하라.
3. `filter_size_surf`와 `filter_size_map`은 각각 무엇에 적용되는가?
4. RViz에서 점군이 쌓여 지도처럼 보인다. 이것은 노드가 점을 누적하고 있다는 증거인가?
5. "우리 노드는 SingleThreadedExecutor니까 ikd-tree에 동시 접근이 없다"는 판단은 옳은가?

> [!info]- 정답 및 해설 보기
> 1. **더 이상 커지지 않는다.** 새로 보는 공간이 없으므로 새 점들이 전부 **격자 중복 제거**(3장 A)에 걸려 버려진다. ikd-tree 크기는 **시간이 아니라 공간(장면의 넓이)에 비례**한다. 만약 이때 뭔가가 계속 커지고 있다면, 그것은 ikd-tree가 아니라 **시각화용 버퍼(B)**다.
> 2. **지도가 매 프레임 바뀌는데 최근접 검색도 매 프레임 수천 번 해야 하기 때문이다.** 일반 k-d tree는 점을 넣고 빼면 균형이 무너져 전체 재구축이 필요한데, 그 비용은 매 프레임 감당할 수 없다. ikd-tree는 증분 삽입/삭제 + **문제가 생긴 서브트리만** 부분 재구축(+큰 것은 별도 스레드)으로 이를 푼다.
> 3. `filter_size_surf`는 **이번에 들어온 스캔(입력)**을, `filter_size_map`은 **저장된 지도(ikd-tree)**를 격자로 솎는다. 이름이 비슷하지만 적용 대상이 완전히 다르다. 그리고 그 위에 `point_filter_num`(개수 기반 솎기)이 하나 더 있어서, **상류인 `point_filter_num`을 조정하지 않으면 하류의 `filter_size_surf`를 줄여도 효과가 안 난다.**
> 4. **아니다.** RViz Display의 **Decay Time** 설정이 지난 메시지를 화면에 남기고 있는 것이다. `/cloud_registered`는 매번 **현재 스캔만** 담아 발행한다. 누적이 **토픽이 아니라 보는 쪽에서** 일어나는 전형적 사례이며, 이 오해가 실제 사고 조사에서 진단을 며칠 지연시킨 적이 있다.
> 5. **옳지 않다.** ikd-Tree는 **자체 rebuild 스레드를 돌린다**(2.2절). 따라서 우리 노드가 콜백을 하나씩 처리하더라도, **트리 입장에서는 항상 "메인 + rebuild" 2자 동시 접근 상태**다. 이 가정을 확인 없이 믿은 결과가 [[09_사례연구_28km_발산과_ROS2_포팅_회귀\|둠둠 09]]의 28km 발산이다. 라이브러리 소스에서 스레드 생성을 grep하는 것은 몇 초면 된다.
