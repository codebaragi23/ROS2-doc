## 1. 개요

00에서 "Nav2는 드론에 그대로 쓸 수 없다"고 했다. 이 문서는 **정확히 무엇이 안 되고, Nav2 내비게이션에서 배운 것 중 무엇을 살릴 수 있으며, 무엇으로 대체하는지**를 정리한다.

## 2. 핵심 개념: Nav2의 무엇이 걸림돌인가

### 2.1 근본 원인 — costmap이 2차원 자료구조다

Nav2 내비게이션 02에서 배운 costmap은 `nav_msgs/OccupancyGrid` 기반이다. 이 메시지는 **평면 격자 하나**이며 높이 축이 아예 없다.

```text
[2D costmap]   각 셀 = (x, y) → 0~254 비용값       ← 높이 정보 없음
[드론에 필요]  각 복셀 = (x, y, z) → 점유/빈공간/미지
```

즉 "책상 아래로 통과", "선반 위로 넘어가기" 같은 판단을 **자료구조 차원에서 표현할 수 없다.** 파라미터 조정으로 해결되는 문제가 아니다.

> **주의**: Nav2에 `voxel_layer`라는 3D 데이터를 다루는 레이어가 있지만, 이것은 **3D 센서 데이터를 받아 2D costmap으로 투영**하는 용도다. 최종 출력은 여전히 2D이므로 드론의 3D 계획에는 쓸 수 없다.

### 2.2 그 밖에 성립하지 않는 전제들

| Nav2 요소 | 드론에서 성립하지 않는 이유 |
|---|---|
| `robot_radius` / `footprint` | 로봇을 **평면 위 원/다각형**으로 근사. 드론은 3차원 부피로 다뤄야 함 |
| `base_footprint` 기준 계산 | 바닥 투영 개념 자체가 없음(01 2.1절) |
| Spin recovery(제자리 회전) | 드론도 yaw 회전은 가능하지만, "막혔을 때 회전하면 풀린다"는 전제가 3D에서는 약함 — 위/아래로 피하는 것이 더 자연스러움 |
| `DiffDrive`/`Omni` 운동 모델 | 멀티로터는 6자유도 + 추력/자세 결합 동역학. 평면 운동 모델로 표현 불가 |

## 3. 핵심 개념: 무엇을 살리고 무엇을 바꾸는가

Nav2 내비게이션 전체를 버리는 것은 아니다. **개념 계층별로 재사용 가능성이 다르다.**

| Nav2 내비게이션에서 배운 것 | 드론에서 |
|---|---|
| **Behavior Tree 구조**(Nav2 내비게이션 05) | ✅ **그대로 재사용 가능.** "본 작업 실패 → 복구 시도 → 재시도"라는 구조는 드론에서도 동일하게 유효하며, BT 라이브러리도 그대로 쓸 수 있다 |
| **Action 기반 중첩 구조**(Nav2 내비게이션 00-1) | ✅ **그대로 재사용 가능.** 목표 전송·피드백·취소라는 인터페이스 패턴은 로봇 종류와 무관 |
| **경로 계획 = 탐색 문제**라는 사고(Nav2 내비게이션 03의 A*) | ✅ **개념은 이전됨.** 격자가 2D 셀에서 3D 복셀로 바뀔 뿐 A* 탐색 자체는 동일 |
| **비용 지도 개념**(Nav2 내비게이션 02) | 🔶 **개념은 유지, 자료구조는 교체.** "장애물 주변에 여유를 둔다(inflation)"는 발상은 3D에서도 그대로 필요 |
| **costmap_2d 구현체**(Nav2 내비게이션 02) | ❌ **교체 필요** — 2.1절 |
| **SmacPlanner2D 등 planner 플러그인**(Nav2 내비게이션 03) | ❌ **교체 필요** |
| **MPPI 컨트롤러**(Nav2 내비게이션 04) | ❌ **교체 필요.** 다만 "후보를 샘플링해 비용으로 평가한다"는 MPPI의 사고방식 자체는 3D 버전으로 존재함 |
| **velocity_smoother**(Nav2 내비게이션 06) | 🔶 개념은 유효하나, 드론은 FC가 자체적으로 부드러운 추종을 수행하므로 역할이 줄어듦 |

## 4. 핵심 개념: 3D 대체 스택

### 4.1 지도 — OctoMap (복셀 기반 3D 점유 지도)

2D occupancy grid의 3D 대응물이다.

- 공간을 정육면체(복셀)로 나누고 각 복셀을 **점유/빈공간/미지** 세 상태로 관리한다 — Nav2 내비게이션 02에서 배운 2D 격자의 세 상태와 같은 발상이다.
- **옥트리(octree)** 구조를 써서, 빈 공간이 넓게 이어진 구역은 큰 덩어리 하나로 묶어 저장한다. 덕분에 3차원인데도 메모리가 감당 가능한 수준으로 유지된다.
- RTAB-Map이 이미 3D 포인트클라우드를 만들고 있으므로(지도제작 00 3장), 그것을 OctoMap으로 변환해 쓰는 경로가 자연스럽다.

### 4.2 경로 계획 — 3D 탐색 또는 샘플링 기반

| 방식 | 성격 | 비고 |
|---|---|---|
| **3D A\*** | Nav2 내비게이션 03에서 배운 A*를 복셀 격자로 확장 | 개념이 익숙해 진입이 쉬움. 공간이 넓으면 탐색량 급증 |
| **RRT / RRT\*** | 무작위로 점을 뿌려 트리를 뻗어가며 경로를 찾는 샘플링 방식 | 고차원·넓은 공간에 유리. OMPL 라이브러리로 제공 |
| **MoveIt 2 + OMPL** | 로봇팔용으로 만들어졌지만 3D 충돌 검사 + OMPL 플래너를 그대로 활용 가능 | 성숙한 구현체를 재사용할 수 있음 |

### 4.3 통합 스택 — Nav2 구조를 3D로 옮긴 시도들

Nav2의 아키텍처(BT + planner + controller 분리)를 유지하면서 내부만 3D로 바꾼 오픈소스 프로젝트들이 있다.

- **[nav3d](https://github.com/saviodp7/nav3d)** — Nav2에서 영감을 받은 UAV용 3D 스택. ROS2 + MoveIt2 + OctoMap + Behavior Tree + PX4 offboard 조합.
- **[nav_drone](https://github.com/slaghuis/nav_drone)** — 드론용 3D 내비게이션 노드 모음. 로봇 주변에 OctoMap 기반 영역을 유지하며 Nav2의 costmap 역할을 대체.

이런 프로젝트를 그대로 쓰든 참고만 하든, **"Nav2의 어느 계층을 유지하고 어느 계층을 갈아끼울 것인가"라는 3장의 판단이 선행되어야 한다.**

## 5. 이 프로젝트에서의 적용 (X3 경험의 이전)

- Nav2 내비게이션에서 튜닝한 **파라미터 값들(`inflation_radius`, `robot_radius`, MPPI critic weight 등)은 재사용 불가**하다. 다만 "inflation을 키우면 좁은 통로를 못 지나간다" 같은 **튜닝 감각은 3D에서도 그대로 통한다.**
- 07에서 배운 진단 원칙("Nav2 내비게이션 문제인지 Relocalization 심화 문제인지부터 나눈다")은 드론에서 **"경로 계획 문제인지 상태 추정 문제인지부터 나눈다"**로 그대로 이전된다 — 드론에서는 후자가 원인인 경우가 훨씬 많다(01).
- RTAB-Map으로 3D 포인트클라우드를 만드는 경험(지도제작 00~02)은 4.1절의 OctoMap 입력으로 직접 이어진다.

## 6. 진단 관점

- **"경로가 아예 안 나온다"** → 2D일 때와 마찬가지로 먼저 **지도가 실제로 채워졌는지** 확인한다. 3D에서는 "미지(unknown) 복셀이 대부분"인 상태가 훨씬 흔하다 — 드론이 아직 그 공간을 보지 못했기 때문이다.
- **"통과할 수 있는 틈인데 못 지나간다"** → 3D inflation 반경이 드론 실제 크기 대비 과도한지 확인. 프로펠러 포함 폭으로 계산해야 한다.
- **"계획은 나오는데 드론이 안 따라간다"** → 경로 계획 문제가 아니라 02의 setpoint 스트리밍 또는 01의 상태 추정 문제일 가능성이 높다.
- **연산 부하** → 3D 지도와 3D 탐색은 2D보다 훨씬 무겁다. Jetson에서 심화 시리즈의 SLAM까지 함께 돌린다면 CPU 예산을 미리 계산해야 한다.
