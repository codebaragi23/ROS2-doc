## 1. 개요

[[02_빠른_적용_로드맵과_체크리스트|02]]의 Phase 1은 "FAST-LIO2가 ROS2에서 정상 빌드·실행됨"이라는 체크박스 한 줄이었다. **실제로 그 한 줄에 도달하기까지 여덟 군데에서 막혔다.**

이 문서는 절차서가 아니다. 절차만 필요하다면 벤더 문서를 보면 된다. 여기 모은 것은 **막혔던 지점과 그 이유**이며, 그중 몇 개는 이 프로젝트 밖에서도 그대로 통하는 진단 패턴이다.

특히 6장의 `dev_type` 사례는 **이 vault 전체에서 가장 교육 가치가 높은 진단 사례** 중 하나다. "정상 응답을 받고도 아무 로그 없이 무시한다"는 실패 모드가 어떤 것인지, 그리고 그럴 때 어디까지 내려가야 하는지를 보여준다.

## 2. 핵심 개념: 이더넷 LiDAR는 시리얼 센서와 근본적으로 다르다

[[03_센서_연동_LiDAR_C1|응용 03]]에서 붙인 RPLiDAR C1과 대조하면 차이가 선명하다.

| | RPLiDAR C1 (응용 03) | Livox Mid-360S (이 문서) |
|---|---|---|
| 물리 연결 | USB → 시리얼 | **이더넷 → UDP** |
| 꽂으면 생기는 것 | `/dev/ttyUSB0` 장치 파일 | **아무것도 안 생긴다** |
| 첫 관문 | `dialout` 그룹 권한 | **호스트 NIC에 고정 IP 부여** |
| 장치를 못 찾을 때 | `ls /dev/ttyUSB*`로 즉시 확인 | 패킷을 직접 떠봐야 함 |
| 드라이버가 죽는 흔한 이유 | 포트 권한/번호 | **네트워크 설정 또는 장치 식별 불일치** |

즉 **"장치가 보이는가"를 확인하는 방법 자체가 없다.** 시리얼 센서는 커널이 장치 파일을 만들어주므로 존재 여부가 파일 시스템에 드러나지만, 이더넷 장치는 그런 흔적을 남기지 않는다.

전체 연결 사슬은 이렇다.

```
[Mid-360S]  10.0.80.183/24  ← 고정 IP. 끝 옥텟은 장비가 정한다(5장)
    │  UDP
    │   ├─ 56000     detection(장치 발견)
    │   ├─ 56100      명령
    │   └─ 56300/56400 포인트 / IMU
    ▼
[Host NIC] 10.0.80.1/24  ← 사용자가 직접 부여해야 한다
    ▼
[Livox-SDK2]        ← /usr/local에 시스템 전역 설치
    ▼
[livox_ros_driver2] ← 워크스페이스에 vendoring
    ▼
/livox/lidar (CustomMsg, 10Hz),  /livox/imu (200Hz)
```

**이 사슬의 어느 칸이 끊겨도 증상은 똑같다 — 토픽이 안 생긴다.** 그래서 진단이 어렵다.

## 4. 네트워크 계층의 세 함정

### 4.1 호스트에 NIC가 2개인데 컨테이너에는 1개만 보인다

**증상**: 케이블을 꽂았는데 컨테이너 안에서 해당 인터페이스가 없다.

**원인**: 개발 호스트에 물리 이더넷 포트가 둘 있었다(내장 Realtek `enp9s0`, 외장 USB `enp7s0`). **컨테이너가 호스트 네트워크를 쓰는 것처럼 보여도, 호스트의 모든 물리 NIC가 컨테이너 네임스페이스에 자동 노출되지는 않는다.** 실제로 컨테이너 안에서는 하나만 보였다.

**진단**: 안팎에서 목록을 비교한다. 다르면 그게 답이다.

```bash
# 호스트에서
ip -brief link show
lspci | grep -i ethernet
# 컨테이너에서
ls /sys/class/net/
ip -brief link show
```

**해결**: docker-compose를 파고드는 대신 **케이블을 다른 포트로 바꿔 꽂았다.** 두 포트를 스왑해 인터넷을 컨테이너에 안 보이는 쪽으로 옮겼다.

> **교훈**: 소프트웨어 설정을 파기 전에, **되돌리기 쉽고 확실한 물리적 해법**이 있는지 먼저 본다.

### 4.2 컨테이너 안에서는 `ip addr add`가 항상 실패한다

```
RTNETLINK answers: Operation not permitted
```

**원인**: 이 컨테이너 프로세스는 `CAP_NET_ADMIN`을 포함한 **전체 capability를 갖고 있는데도** 거부됐다. 즉 단순 권한 문제가 아니다. 컨테이너의 네트워크 네임스페이스가 그 물리 NIC를 실제로 소유한 네임스페이스가 아니기 때문으로 **추정**된다(정확한 메커니즘은 미확인).

**해결**: 이 명령은 **호스트 터미널에서** 실행한다. 컨테이너 쪽에는 실행 alias 대신 **상태 확인 alias만** 두었다. 처음엔 컨테이너 `.bashrc`에 실행 alias를 넣었다가, 항상 실패한다는 것을 확인하고 확인 전용으로 바꿨다.

> **교훈 둘**: "권한이 있으니 될 것"이라는 추론은 네임스페이스 앞에서 깨진다. 그리고 **항상 실패하는 명령을 alias로 남겨두면 그 자체가 오해의 원인**이 된다 — 되는 것만 남기고 안 되는 것은 안내 문구로 바꾼다.

### 4.3 Jetson에서는 고정 IP를 줘도 곧 사라진다 — NetworkManager

**증상**: `sudo ip addr add 10.0.80.1/24`를 줬는데 잠시 뒤 없어져 있다.

**원인**: `ip addr add`는 **커널에 주소를 넣는 일회성 명령**이라 인터페이스 상태가 바뀌기만 해도 사라진다. 더 결정적으로, Jetson에서는 **NetworkManager가 그 인터페이스를 관리 중**이었다(`nmcli device status`에서 `disconnected`로 표시). NetworkManager는 자기가 관리하는 인터페이스를 자기 프로파일 기준으로 되돌리므로, 바깥에서 손으로 넣은 주소를 지운다.

**해결**: 명령형이 아니라 **선언형 프로파일**로 등록한다.

```bash
sudo nmcli con add type ethernet ifname enP8p1s0 con-name mid360-lidar \
  ip4 10.0.80.1/24 gw4 0.0.0.0 ipv4.never-default yes
sudo nmcli con up mid360-lidar
```

`autoconnect=yes`가 기본이라 재부팅·재연결에도 유지된다. **`gw4 0.0.0.0`과 `ipv4.never-default yes`를 함께 주는 이유는 5.4절에 있다** — 이 선으로는 어디로도 나가지 않는다는 선언이다.

> **교훈**: 같은 리눅스라도 **누가 그 인터페이스의 소유자인가**(수동 / NetworkManager / systemd-networkd)에 따라 정답이 달라진다. 설정이 "사라진다"면 **지운 주체를 먼저 찾는다.**

## 5. 핵심 개념: 두 개의 IP — 호스트 NIC와 라이다

이더넷 LiDAR를 붙일 때 **주소가 두 개** 등장하는데, 둘을 같은 것으로 보면 진단이 통째로 어긋난다. 한 케이블에 붙은 두 장치가 각자 자기 주소를 갖는다.

```
┌──────────────── 유선 케이블 (전용 구간) ────────────────┐
│                                                        │
[Orin] enP8p1s0                              [Mid-360S]
       10.0.80.1                              10.0.80.183
       ↑                                      ↑
       호스트 NIC IP                           라이다 IP
       "내 주소"                               "상대 주소"
```

전화에 비유하면 **NIC IP는 내 번호, 라이다 IP는 거는 번호**다.

### 5.1 네 가지가 다르다

| | 호스트 NIC IP | 라이다 IP |
|---|---|---|
| 누구 것인가 | Orin의 유선 포트 | 라이다 본체 |
| 어디 저장되나 | **Orin의 OS 설정** | **라이다 내부 플래시** |
| 어떻게 바꾸나 | `nmcli` (Orin에서) | Livox Viewer 2 또는 SDK의 `SetLivoxLidarIp()` |
| 끝 옥텟 | **우리가 정한다** (`.1`) | **장비가 정한다** — 시리얼 끝 두 자리에서 나온다 |

**끝 옥텟 차이가 핵심이다.** NIC은 아무 번호나 줘도 되지만, 라이다의 `.183`은 시리얼에서 나온 값이라 우리가 고를 수 없다. 그래서 **대역(앞 세 옥텟)만 맞추고 끝 옥텟은 장비를 따라간다.**

**공식 매뉴얼도 같은 규칙을 적는다** — 출고 기본값은 `192.168.1.1XX`이고, `XX`가 **시리얼 번호 끝 두 자리**다(서브넷 `255.255.255.0`, 권장 호스트 IP `192.168.1.50`).

> 이 규칙은 이 프로젝트에서도 확인됐다. 시리얼 끝이 `83`이라 기본 IP가 `192.168.1.183`이었고, 대역을 `10.0.80.x`로 옮긴 뒤에도 **끝자리 183은 그대로였다.**

### 5.2 설정 파일에서 자리가 다르다

두 주소는 SDK 설정에서 **서로 다른 항목**에 들어가고, 하는 일도 반대다.

```json
"Mid360s": {
  "host_net_info": [{ "host_ip": "10.0.80.1",      ← 여기에 bind 한다 (내가 받을 자리)
                      "point_data_port": 56301 }]
},
"lidar_configs": [{ "ip": "10.0.80.183" }]          ← 여기로 명령을 보낸다 (목적지)
```

흐름으로 보면 이렇다.

```
Orin 10.0.80.1:56101  ──명령──▶  라이다 10.0.80.183:56100
Orin 10.0.80.1:56301  ◀──점군──  라이다
Orin 10.0.80.1:56401  ◀──IMU───  라이다
```

**`host_ip`는 소켓을 여는 주소**라 그 주소가 실제 NIC에 없으면 **커널이 거부한다.** 반면 **라이다 IP는 보내는 목적지**일 뿐이라 틀려도 **소켓은 정상적으로 열린다.**

### 5.3 그래서 증상이 정반대로 나온다

이 프로젝트에서 둘 다 겪었다.

| 틀린 쪽 | 증상 |
|---|---|
| **NIC IP** | `bind failed` / `Failed to init livox lidar sdk` — **드라이버가 아예 안 뜬다** |
| **라이다 IP** | `Init lds lidar success!`는 뜨는데 **점군이 한 장도 안 온다** |

> **두 번째가 훨씬 고약하다.** 로그가 "성공"이라고 말하니 SDK·케이블·전원을 차례로 의심하며 한참 헤매게 된다. 6장의 `dev_type` 불일치가 정확히 이 모습이었고, 그때 라이다는 정상적으로 쏘고 있는데 **커널이 ICMP port unreachable을 413만 건 돌려보내고 있었다.**

**같은 계열의 실패다** — 둘 다 "받을 자리가 없는데 보내는 쪽은 모른다"는 구조다. 조용한 실패를 다루는 일반론은 [[10_실전_조사에서_배운_것|둠둠 10]] 9장에 정리했다.

### 5.4 왜 같은 대역이어야 하나

둘이 같은 케이블(같은 L2 구간)에 있으므로 서로를 **ARP로 찾는다.** 대역이 다르면 서로를 "이 랜선 너머"가 아니라 "라우터 건너편"으로 보고 **게이트웨이를 찾는데, 직결선에는 게이트웨이가 없다.**

그래서 이 인터페이스는 게이트웨이를 `0.0.0.0`으로 두고, `ipv4.never-default yes`를 붙인다 — **이 선으로는 어디로도 나가지 않는다**는 선언이다. 기본 경로가 이쪽으로 잡히면 인터넷이 끊긴다.

### 5.5 런치 진입에서 미리 잡기

두 주소 모두 **실행 전에 확인할 수 있다.** 성질이 다르므로 확인 방법도 다르다.

| 대상 | 확인 방법 |
|---|---|
| `host_ip` | **실제로 bind를 시도해 본다.** 성공하면 그 주소가 NIC에 있다는 뜻 |
| 라이다 IP | **같은 `/24`에 있는지 본다.** 실제 응답 여부는 이 단계에서 알 수 없다 |

이 프로젝트는 이 두 검사를 런치 진입 시점에 수행하는 preflight를 넣었다. **"성공했다는 로그를 보고 30분 헤매는 것"보다 "시작 전에 거부당하는 것"이 훨씬 싸다.**

### 5.6 라이다에도 호스트 주소가 저장될 수 있다

SDK 헤더를 보면 라이다 쪽에 **"어디로 보낼지"를 스트림별로 저장하는 API**가 있다 — 상태 정보용(`SetLivoxLidarStateInfoHostIPCfg`), 점군용(`SetLivoxLidarPointDataHostIPCfg`), IMU용(`SetLivoxLidarImuDataHostIPCfg`). 즉 호스트 주소가 **라이다 내부에 스트림마다 따로 남아 있을 수 있다.**

다만 이 프로젝트의 경로에서는 **매 실행 시 JSON의 `host_ip`를 SDK가 연결 시점에 알려주는 방식**으로 동작하고 있어, 라이다 쪽 저장값을 따로 건드릴 일은 없었다.

> **그래도 알아둘 가치가 있다**: NIC IP를 바꿨는데도 점군이 안 오면, **라이다에 남은 옛 호스트 주소**를 의심할 자리다.

## 6. ★핵심 사례: `dev_type` 불일치 — 응답을 받고도 조용히 버린다

가장 오래 걸린 지점이고, 교육 가치도 가장 높다.

### 6.1 증상 — 모든 계층이 정상인데 아무 일도 안 일어난다

- 네트워크는 **완전히 정상**이었다. tcpdump로 Mid-360S가 point/imu 데이터와 detection 응답을 계속 보내는 것까지 확인했다.
- 그런데 드라이버를 실행하면 `/livox/lidar`, `/livox/imu` 토픽이 **전혀 생성되지 않는다.**
- 드라이버 로그는 `GetFreeIndex key:...` 한 줄에서 멈춘다. **에러 메시지조차 없다.**
- SDK의 discovery CLI도 아무 출력 없이 timeout된다.

### 6.2 근본 원인 — 한 줄의 조용한 `return`

Livox-SDK2의 장치 관리 코드에 이런 부분이 있다.

```cpp
// sdk_core/device_manager.cpp
if (type_lidars_cfg_map_.find(detection_data->dev_type) == type_lidars_cfg_map_.end()) {
  return;   // 아무 로그도 없이 조용히 무시
}
```

`type_lidars_cfg_map_`은 `MID360_config.json`의 **최상위 키**로부터 채워진다. 등록된 키는 `"HAP"`, `"MID360"`, `"Mid360s"`, `"Avia2"`이고 각각 dev_type 상수에 매핑된다.

```c
// include/livox_lidar_def.h
kLivoxLidarTypeMid360   = 9,
kLivoxLidarTypeMid360s  = 35,
```

**이 개체는 dev_type 35, 즉 `Mid360s`로 응답했다.** 그런데 vendoring된 기본 config는 `"MID360"`(=9)이었으므로, SDK는 정상 응답을 받고도 조회에 실패해 **로그 한 줄 없이 return** 해버렸다.

> **여기에 이 사례의 진짜 교훈이 있다.** 당시에는 이것을 "라벨은 Mid-360인데 프로토콜만 다른 리비전으로 답한다"는 **이상 현상**으로 기록했다. 하지만 나중에 확인해 보니 **이 장비는 처음부터 Mid-360S였다.** 즉 이상한 것은 장비가 아니라 **우리가 알고 있던 모델명**이었고, **프로토콜은 줄곧 사실을 말하고 있었다.**
>
> `dev_type 35`는 오류 신호가 아니라 **정답**이었는데, 그것을 "예외"로 분류하는 바람에 원인 규명이 늦어졌다. **관측이 내 전제와 어긋날 때, 틀린 쪽이 전제일 수 있다.**

### 6.3 어떻게 찾았나 — 프로토콜 레벨로 내려가기

로그가 없으므로 로그를 아무리 봐도 안 나온다. **패킷을 직접 읽는 것 말고는 방법이 없었다.**

```bash
sudo timeout 8 tcpdump -i <interface> -n -X -c 4 'src 10.0.80.183 and port 56000'
```

detection 응답의 구조는 SDK 헤더에 정의되어 있다.

```
DetectionData:  ret_code(1B) + dev_type(1B) + sn(16B) + lidar_ip(4B) + cmd_port(2B)
```

IP 헤더(20B) + UDP 헤더(8B) 다음이 payload 시작이므로, **payload의 2번째 바이트가 `dev_type`**이다. 이 개체는 그 바이트가 `0x23` = 35였다.

### 6.4 수정 — JSON 키 한 줄

```json
{
  "Mid360s": {    // "MID360" 대신 (대소문자까지 정확히 일치해야 한다)
    ...
  }
}
```

바꾸고 재빌드하자 즉시 정상 초기화 시퀀스(`successfully set lidar attitude` → `successfully enable Livox Lidar imu`)가 나오고 토픽이 떴다.

**지금이라면 더 나은 방법이 있다.** `livox_ros_driver2`는 **1.2.6부터 Mid-360S를 정식 지원**하며, 전용 파일 `config/MID360s_config.json`과 `launch_ROS2/msg_MID360s_launch.py`를 함께 제공한다. 키를 손으로 고치는 대신 **전용 파일을 쓰는 것이 옳다.**

> **⚠ 그리고 여기에 함정이 둘 더 있다.**
>
> **① 파일명과 JSON 키의 대소문자가 다르다.** 파일은 `MID360s_config.json`(소문자 s)인데 그 안의 최상위 키는 `"Mid360s"`(대문자 M)다. SDK는 정확히 일치하는 키만 찾으므로 `"MID360S"`나 `"Mid360S"`로 적으면 **또 조용히 실패한다.**
>
> **② `host_net_info`의 자료형이 다르다.** Mid-360용 config에서는 **객체**인데, Mid-360S용에서는 **객체의 배열**이다. 그래서 **기존 Mid-360 설정을 복사해 키 이름만 바꾸면 동작하지 않는다** — 5.2절의 예시가 배열 형태인 이유가 이것이다.

### 6.5 이 수정의 위험 — 반대 방향으로 깨진다

**이 설정은 Mid-360S 전용이다.** 형제 모델인 **Mid-360**(dev_type 9)을 같은 설정으로 연결하면 이번과 **정확히 반대로** 실패한다. 두 모델은 겉모습으로 구분되지 않으므로, **새 유닛을 처음 붙일 때는 hex 디코딩으로 dev_type을 먼저 확인한다** — 이것이 모델명을 확인하는 가장 확실한 방법이다.

> **교훈 셋**
>
> 1. **"출력이 없다"는 "장치가 없다"가 아니다.** discovery 도구가 조용히 끝나는데 tcpdump에는 트래픽이 보이면, 십중팔구 매칭 실패다.
> 2. **조용한 실패(silent failure)는 최악의 실패 모드다.** 이 SDK는 조회 실패를 정상 흐름으로 취급해 로그조차 남기지 않는다. 코드를 읽지 않았다면 영원히 못 찾았을 것이다.
> 3. **장비가 스스로 밝히는 정체가, 내가 알고 있는 제품명보다 정확하다.** 이 사례에서 `dev_type 35`는 처음부터 옳았고 틀린 것은 우리 쪽 인식이었다. **하드웨어를 다룰 때 "무슨 모델인지 안다"는 것도 검증 대상이다.**

## 7. 빌드·배포 계층의 두 함정

### 7.1 x86_64 산출물을 aarch64 Jetson에 쓸 수 없다

`colcon build`/`cmake` 산출물은 **아키텍처 종속**이다. Dev Container(x86_64)에서 만든 `build/`, `install/`을 Jetson(aarch64)에 복사해 쓸 수 없고, SDK 설치와 드라이버 빌드를 **양쪽에서 각각 native로** 해야 한다.

실측 빌드 시간(같은 소스, 다른 아키텍처):

| 대상 | livox_ros_driver2 | fast_lio | 합계 |
|---|---|---|---|
| Dev Container(x86_64) | 12.7초 | 54.3초 | **1분 7초** |
| Jetson Orin(aarch64) | 28.7초 | 2분 23초 | **2분 52초** |

여기에 이 프로젝트 고유의 제약이 하나 더 있었다. **Jetson에는 GitHub 인증이 없어 `git clone`이 실제로 실패했다.** 그래서 `git pull` 대신 **소스를 rsync로 밀어넣는** 방식을 택했다.

> **교훈**: **인증 경계는 배포 경로 설계를 바꾼다.** Jetson에 인증을 심는 대신 push 방식(rsync)으로 간 것은 인증 표면을 줄이는 선택이다.

### 7.2 config를 고쳤는데 동작이 그대로다

**원인**: colcon의 기본 동작은 `install/`에 파일을 **복사**하는 것이다. launch가 실제로 읽는 파일은 `install/.../config/mid360.yaml`이지 `src/`의 원본이 아니다. 재빌드하지 않으면 예전 사본이 계속 읽힌다. 같은 함정이 드라이버의 `MID360_config.json`에도 있다 — 6.4절의 dev_type 키를 고칠 때마다 재빌드해야 반영된다.

**해결**: 워크스페이스 루트에 `colcon_defaults.yaml`을 두어 `colcon build`가 기본으로 `--symlink-install`을 쓰게 했다. config/launch/rviz처럼 컴파일이 필요 없는 파일이 심볼릭 링크로 설치되어 **수정이 재빌드 없이 즉시 반영**된다.

```bash
ls -la install/fast_lio/share/fast_lio/config/mid360.yaml
# lrwxrwxrwx ... -> .../src/FAST_LIO_ROS2/config/mid360.yaml  이면 정상
```

주의할 점 둘: C++ 소스는 여전히 재빌드가 필요하고, 복사 방식으로 만들어진 기존 `install/`이 남아 있으면 두 방식이 섞여 더 헷갈린다 — 모드를 바꿀 때는 해당 패키지의 `build/`·`install/`을 지우고 새로 빌드한다. 그리고 `livox_ros_driver2`의 `build.sh`는 워크스페이스 루트의 `build/ install/ log/`를 **통째로 지운 뒤** 빌드하므로(ROS1/ROS2 겸용 소스라 파일을 치환한다) 다른 패키지 산출물도 같이 날아간다.

> **교훈**: **"내가 고친 파일"과 "프로그램이 읽는 파일"이 다를 수 있다.** 설정을 바꿨는데 동작이 안 변하면, 코드를 의심하기 전에 **읽히는 경로가 어디인지** 먼저 확인한다. [[04_colcon_빌드_오류_모음|응용 04]]가 다루는 빌드 함정의 실제 사례다.

## 8. `ping`이 안 되는데 정상이다 — 진단 도구의 거짓 음성

**증상**: `ping 10.0.80.183`이 무응답. 네트워크 preflight 스크립트도 실패로 판정.

**그런데 토픽은 정상 발행됐다.** 즉 **이 장치는 ICMP echo에 응답하지 않는 것으로 보인다**(임베디드 LiDAR에서 흔한 동작, 확증은 없음).

**의미**: `ping` 실패를 연결 불량의 증거로 쓰면 안 된다. 연결성 판정은 이 순서로 한다.

```
1. tcpdump로 실제 UDP 트래픽이 오는가      ← 가장 확실
2. 드라이버 로그가 초기화 시퀀스를 끝까지 진행하는가
3. ros2 topic hz로 실제 데이터가 흐르는가
(ping은 판정 근거에서 제외)
```

> **교훈**: **진단 도구가 대상에 대해 하는 가정**을 의심한다. `ping`은 "정상 장치는 ICMP에 답한다"를 가정하는데, 임베디드 장치에는 그 가정이 성립하지 않는 경우가 많다. **거짓 음성을 내는 체크를 preflight 스크립트에 남겨두면 그 스크립트 자체가 오진의 원인**이 된다.

## 9. 미해결: 도메인 분리와 원격 RViz

이건 **아직 해결하지 못했고, 그래서 오히려 교육 가치가 있다.**

**목표**: 무거운 연산(드라이버 + FAST-LIO2)은 Jetson에서 돌리고, 시각화(RViz)는 Dev Container에서 네트워크로 구독한다. Jetson은 헤드리스 운용이 기본이라 로컬 RViz가 비현실적이기 때문이다.

**증상 1** (`ROS_DOMAIN_ID=24`): 컨테이너에서 `ros2 topic list`에 토픽이 **보이기는 하는데 데이터가 전혀 안 온다**. CycloneDDS 트레이싱으로 좁힌 결과, discovery로 받은 참가자들이 광고하는 unicast locator가 전부 **Jetson의 Mid-360S 전용 NIC 주소**였다 — 컨테이너가 도달할 수 없는 주소다. 게다가 그 참가자들의 PID가 실제 실행 중인 프로세스와 일치하지 않았다(오래된 광고가 도메인에 떠돌고 있었다).

**증상 2** (도메인을 34로 분리): 오염을 피하려 분리했더니 **discovery 자체가 아예 안 됐다.** 24에서는 최소한 이름은 떴었다.

**현재 가설**(추정): 단순 도메인 오염이 아니라 **랩 WiFi(공유 AP)가 특정 멀티캐스트 그룹/포트만 통과시키는 것**으로 보인다(도메인 ID가 곧 멀티캐스트 포트를 결정한다). **우리가 관리하는 네트워크가 아니라 확정하지 못했다.**

**현실적 대안**: ① 호스트 ↔ Jetson 유선 직결로 AP를 우회 ② 네트워크 관리자에게 정책 문의 ③ **실시간 원격 뷰를 포기**하고 세션 후 `.pcd`를 가져와 오프라인 확인(가장 현실적).

> **교훈 셋**
>
> 1. **"discovery는 되는데 데이터가 안 온다"는 대부분 주소 광고 문제다.** DDS 참가자는 자기가 도달 가능하다고 **스스로 믿는** 주소를 광고한다. NIC가 여러 개인 호스트에서는 엉뚱한 NIC 주소를 광고할 수 있다. [[01_DDS와_QoS_이해하기|응용 01]]이 다룬 "토픽은 보이는데 데이터가 없다"의 또 다른 원인 계층이다.
> 2. **직관적인 해결책이 상황을 악화시킬 수 있다.** 24가 "우연히 부분적으로라도 되던 유일한 값"이었을 가능성을 데이터가 가리켰다.
> 3. **내가 통제할 수 없는 계층이 있으면 거기서 조사가 멈춘다.** 그럴 때는 원인 규명을 무한히 시도하는 대신 **우회 경로**를 설계한다.

| NIC IP를 바꿨는데도 점군이 안 옴 | 라이다에 남은 **옛 호스트 주소**를 의심 | 5.6 |
| 라이다를 붙이니 인터넷이 끊김 | 기본 경로가 이 인터페이스로 잡힌 것 — `ipv4.never-default` 확인 | 5.4 |
| 토픽 이름은 보이는데 `echo`가 timeout | DDS 참가자가 광고하는 locator 주소 확인(도달 불가 NIC 주소일 수 있음) | 9장 |

## 11. 이해도 점검

1. 드라이버를 실행했는데 토픽이 안 생기고 에러 로그도 없다. tcpdump에는 LiDAR가 보낸 UDP 패킷이 보인다. 무엇을 의심하고, 어떻게 확인하는가?
2. `ping`이 실패했다. 이것을 "연결 불량"의 증거로 쓸 수 있는가?
3. 컨테이너 안에서 `ip addr add`가 `Operation not permitted`로 실패한다. 전체 capability를 갖고 있는데도 그렇다. 어떻게 대응하는가?
4. Jetson에서 고정 IP를 줬는데 자꾸 사라진다. 원인은 무엇이고 올바른 해법은?
5. `mid360.yaml`을 고치고 실행했는데 동작이 그대로다. 코드를 의심하기 전에 무엇을 확인하는가?
6. 설정의 `host_ip`와 `lidar_configs[].ip`는 각각 무엇이고, 하나씩 틀렸을 때 증상이 어떻게 다른가?
7. 라이다 IP의 끝자리는 왜 우리가 고를 수 없는가? 그리고 이 인터페이스에 `ipv4.never-default`를 붙이는 이유는?

> [!info]- 정답 및 해설 보기
> 1. **장치 식별(`dev_type`) 불일치**를 의심한다. 네트워크가 정상인데 SDK가 조용히 무시하는 대표적 상황이다. `tcpdump -X`로 detection 응답을 떠서 **payload의 2번째 바이트**를 읽고, 그 값에 대응하는 키(`"MID360"`=9 / `"Mid360s"`=35)로 `MID360_config.json`의 최상위 키를 맞춘다. 고친 뒤 **재빌드**해야 `install/`에 반영된다(7.2절과 연결된다).
> 2. **쓸 수 없다.** 이 장치는 정상 동작 중에도 ICMP에 응답하지 않는다. `ping`은 "정상 장치는 ICMP에 답한다"를 가정하는데 임베디드 장치에는 그 가정이 자주 깨진다. 판정은 tcpdump(실제 트래픽) → 드라이버 초기화 로그 → `ros2 topic hz` 순으로 한다.
> 3. capability 문제가 아니라 **네트워크 네임스페이스 소유권** 문제이므로 컨테이너 안에서는 해결할 수 없다. **호스트 터미널에서** 주소를 부여하고, 컨테이너에는 실행 명령 대신 **상태 확인용 헬퍼**만 둔다. 항상 실패하는 명령을 alias로 남겨두면 그것 자체가 오해의 원인이 된다.
> 4. **NetworkManager**가 그 인터페이스를 관리하면서, 바깥에서 손으로 넣은 주소를 자기 프로파일 기준으로 되돌린다. `ip addr add`(명령형) 대신 `nmcli con add ... ip4 10.0.80.1/24`(선언형 프로파일)로 등록하면 재부팅에도 유지된다. 일반화하면 — 설정이 "사라진다"면 **지운 주체를 먼저 찾는다.**
> 5. **프로그램이 실제로 읽는 파일 경로**를 확인한다. colcon은 기본적으로 `install/`에 파일을 **복사**하므로, launch가 읽는 것은 `install/.../mid360.yaml`이지 내가 고친 `src/`의 원본이 아니다. `ls -la`로 심볼릭 링크인지 보고, 아니면 재빌드하거나 `--symlink-install`로 전환한다.
> 6. **`host_ip`는 내가 소켓을 여는(bind 하는) 주소**이고, **`lidar_configs[].ip`는 명령을 보내는 목적지**다. 그래서 증상이 정반대다 — `host_ip`가 틀리면 그 주소가 NIC에 없으므로 **커널이 bind를 거부해 드라이버가 아예 안 뜬다**(시끄러운 실패). 라이다 IP가 틀리면 **소켓은 정상적으로 열리므로 `success` 로그가 뜨는데 점군만 안 온다**(조용한 실패). 두 번째가 훨씬 고약하다 — 로그가 성공이라 말하니 엉뚱한 곳을 의심하게 된다.
> 7. 라이다 IP의 끝 옥텟은 **시리얼 번호에서 나오므로 장비가 정한다.** 우리가 맞출 수 있는 것은 **대역(앞 세 옥텟)뿐**이다. 실제로 이 프로젝트에서 대역을 옮겼을 때 끝자리는 그대로였다. `ipv4.never-default`는 **이 직결선이 기본 경로로 잡히지 않게** 하려는 것이다 — 이 구간에는 게이트웨이가 없으므로, 기본 경로가 이쪽으로 잡히면 인터넷이 끊긴다.
