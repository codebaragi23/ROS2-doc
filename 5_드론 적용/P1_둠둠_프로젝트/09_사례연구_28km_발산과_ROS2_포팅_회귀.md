## 1. 개요

[[08_사례연구_정지_상태_발산|08]]에서 원인을 특정했다. 남은 일은 두 가지였다 — **"왜 이런 코드가 존재하는가"**를 알아내는 것과, **고치는 것**이다.

전자는 깔끔하게 풀렸다. 후자에서 **더 큰 사고가 났다.**

> **7장이 이 사례의 핵심이다.** 구조적으로 더 옳은 수정이, 컨테이너 검증까지 통과한 뒤, 실기체에서 **28 km 발산**을 만들었다. 왜 그랬는지가 이 vault 전체에서 가장 일반화 가치가 높은 교훈 중 하나다.

## 2. 출처 추적 — "원래부터 이랬나?"

답은 **아니오**다.

### 2.1 ROS1 원본은 어떻게 했나

FAST-LIO는 원래 **ROS1(Melodic/Noetic) 시대의 프로그램**이다(FAST-LIO 2.0 공개가 2021년). ROS1 원본의 지도 발행 코드는 이랬다.

```cpp
// ROS1 원본 (요약)
if(0) // If you need to see map point, change to "if(1)"
{
    // ikd-tree를 평탄화해서 그대로 복사
    featsFromMap->clear();                       // ← 매번 비운다
    featsFromMap->points = ikdtree.PCL_Storage;  // ← ikd-tree의 스냅샷
}
...
// publish_map(pubLaserCloudMap);                // ← 호출부도 주석 처리
```

**세 가지가 결정적이다.**

1. **데이터 출처가 ikd-tree다.** 자기만의 저장소가 아니라 **(A)를 베낀 스냅샷**이다.
2. **매번 비운다.** 크기가 항상 ikd-tree와 같으므로 [[04-4_ikd-tree와_LIO의_지도_관리|04-4]] 3장의 자기 관리 장치를 **그대로 물려받는다. 절대 무한히 커질 수 없다.**
3. **기본값이 꺼져 있다.** ROS1 사용자에게 이 토픽은 사실상 존재하지 않았다. 지도는 **RViz가 Decay Time으로 대신 쌓아줬다**([[04-4_ikd-tree와_LIO의_지도_관리|04-4]] 5.2절).

그리고 **처리 구조 자체도 달랐다.**

```cpp
// ROS1: 하나의 메인 루프가 전부를 순서대로 처리
while (status) {
    ros::spinOnce();                  // 메시지를 버퍼에 담기만 함
    if(sync_packages(Measures)) { ... EKF, 지도 갱신, 발행 전부 여기서 순서대로 ... }
}
```

**"지도 발행"이 별도 스케줄로 끼어들 여지가 자체가 없다.** [[08_사례연구_정지_상태_발산|08]] 6.3절의 사고 구조가 **ROS1에서는 성립조차 하지 않는다.**

### 2.2 ROS2 포팅에서 무엇이 바뀌었나

커밋 단위로 추적한 결과다.

| 커밋 | 무엇을 했나 |
|---|---|
| `Ericsii/FAST_LIO_ROS2` **"fix: Map publish"** | 지도 발행을 **ikd-tree 스냅샷 → 자체 버퍼 누적**으로 교체. 동시에 ikd-tree 복사 블록을 **`if(0)`으로 꺼버림**. 이 시점엔 스로틀이 남아 있었다 |
| **"feat: Add pcd save"** | **그 스로틀마저 제거.** 저장 서비스를 추가하며 저장 대상도 그 누적 버퍼로 지정. 동시에 원래 살아있던 PCD 자동 저장 블록을 통째로 주석 처리(**여기서 죽은 코드가 생겼다**) |
| `hku-mars/FAST_LIO` **PR #306 "ROS2 Support"** (2024-02-25 머지) | 위 결과물을 **본가가 그대로 수용.** 이 경로에서는 커뮤니티 포크가 upstream이다 |

교체의 흔적이 지금 소스에도 주석으로 남아 있다.

```cpp
// sensor_msgs::msg::PointCloud2 laserCloudMap;
// pcl::toROSMsg(*featsFromMap, laserCloudMap);   ← 옛 ROS1 코드
```

> **부수 발견 — PCD 자동 저장은 죽은 코드다.** 프로젝트 가이드가 초기에 "정상 종료하면 PCD가 자동 저장된다"고 썼는데 **틀렸다.** 종료 루틴의 조건은 맞지만, 그 버퍼를 **채우는 코드가 통째로 주석 처리**되어 있어 조건이 **항상 거짓**이다. 실제로 동작하는 저장 방법은 `/map_save` 서비스뿐이다. **문서가 코드를 확인하지 않고 쓰인 사례**이며, 소스를 읽어 정정했다.

### 2.3 포크를 잘못 골라서 생긴 문제인가? — 아니다

`laserMapping.cpp`를 파일 해시로 직접 대조했다.

| 대상 | 결과 |
|---|---|
| 우리가 vendoring한 원본 | 기준 |
| 커뮤니티 포크 A | **바이트 동일** |
| `Ericsii/FAST_LIO_ROS2` | **바이트 동일** |
| `hku-mars/FAST_LIO` @ `ROS2` (공식) | 2줄 차이 (TF 타임스탬프 출처 — 이번 문제와 무관) |

> **저장소 선택으로 피할 수 있는 문제가 아니었다.** ROS1 `main` 브랜치를 쓰지 않는 한 ROS2 계열은 공식이든 커뮤니티 포크든 전부 같은 코드다. 그리고 **우리는 아무것도 포팅하지 않았다** — 이미 포팅된 결과물을 가져다 썼을 뿐이다.

### 2.4 포팅한 사람에게는 정당한 동기가 있었다

이 점이 중요하다. ROS1에서 이 토픽은 **빈 토픽**이었다. 사용자가 보기엔 **"고장난 기능"**이다. 그걸 "고친다(fix)"고 한 것이 커밋 이름이다. 다만 **가장 간단한 방법**을 골랐다 — 매번 스캔을 한 곳에 계속 더하기.

> **교훈**: 포팅은 기능뿐 아니라 **"왜 그렇게 안 했는지"까지** 옮겨야 한다. ROS1에서 꺼져 있던 건 실수가 아니라 **선택**이었을 수 있는데, 포팅 과정에서 "고장난 기능"으로 재해석됐다.
>
> 코드를 교체할 때는 **원래 코드가 보장하던 성질**을 목록화한다. 여기서는 ①출처가 자기 관리되는 자료구조 ②매번 clear ③기본 비활성 — **세 가지가 전부 사라졌다.**

### 2.5 알려졌지만 고쳐지지 않았다

- 우리와 똑같은 증상이 **issue #449**로 보고됐고 리포터가 원인까지 정확히 지목했다. 그런데 **유지보수자 코멘트 하나 없이 stale 봇이 닫았다.**
- 관련 메모리 이슈들도 이 건으로 머지된 수정이 없다.
- **공식 저장소에는 지금도 수정이 머지되지 않았다.**
- **포크 한 곳에는 수정이 있다**: `tu-darmstadt-ros-pkg/FAST_LIO`가 ①발행 전 voxel 다운샘플(PR #1) ②새 스캔이 없으면 중복 추가 안 함(PR #2) ③구독자 없으면 건너뜀 — 세 가지를 **차례로** 넣어 현재는 셋이 함께 있다. 우리 수정은 ①에 독립적으로 도달했다.

> **실무적 함의**: "공식 저장소 + 5천 스타"는 **출처의 신뢰성**을 말해주지만 **활발한 유지보수를 보장하지 않는다.** 공식 ROS2 브랜치는 사실상 커뮤니티 포팅을 머지한 것이고, 그 뒤로 갱신이 드물다. 저장소를 고를 때 두 축(출처 / 유지보수 활동)을 **따로** 봐야 한다.

## 3. 두 번째 사고 — "더 정석적인" 수정이 28km 발산을 만들다

### 3.1 동기는 완벽했다

[[04-4_ikd-tree와_LIO의_지도_관리|04-4]] 3장에서 봤듯 **ikd-tree는 이미 중복 제거와 공간 정리가 되어 있다.** 없는 걸 새로 만들 게 아니라 있는 걸 쓰는 게 맞다 — **2.1절에서 본 ROS1 원본이 하려던 바로 그 방식이다.**

그래서 "지도 발행을 ikd-tree 스냅샷에서 가져오기" 옵션을 만들었다. 논리적으로 흠잡을 데가 없다.

### 3.2 컨테이너 재생 결과는 기대 이상이었다

| 경과 | 기존 누적 방식 | ikd-tree 스냅샷 |
|---|---|---|
| 29초 | 10,338점 | 532점 |
| 149초 | 54,643점 | 652점 |
| 329초 | **121,219점 / 5.8 MB** | **677점** |
| 양상 | 선형(초당 336점) | **포화**(60초당 8점) |

누적오차는 0.052 m로 **완전히 동일** — 발행 소스가 위치추정에 영향이 없음이 확인됐다. RSS 증가도 줄었다. **voxel 패치조차 불필요해진다.**

### 3.3 그리고 Jetson 실기에서 추정 위치가 28 km까지 발산했다

### 3.4 무엇을 놓쳤나

**트리를 평탄화하는 함수는 안전한 읽기 연산이 아니었다.**

ikd-Tree의 정상 연산(최근접 검색 등)은 재구축 중인 서브트리를 건드리는지 **확인하고, 필요하면 락을 잡는다.**

```cpp
// 정상 연산: 가드가 있다
if (Rebuild_Ptr == nullptr || *Rebuild_Ptr != Root_Node) {
    Search(Root_Node, ...);
} else {
    pthread_mutex_lock(&search_flag_mutex);   // 락으로 보호
    ...
}
```

**그런데 평탄화 함수에는 그 확인이 없다.**

```cpp
void KD_TREE<PointType>::flatten(KD_TREE_NODE *root, PointVector &Storage, ...)
{
    if (root == nullptr) return;
    Push_Down(root);                     // ← 노드를 **수정**한다 (읽기가 아니다!)
    if (!root->point_deleted) Storage.push_back(root->point);
    flatten(root->left_son_ptr, ...);    // ← rebuild 스레드가 갈아끼울 수 있는 포인터
    flatten(root->right_son_ptr, ...);
}
```

그리고 [[04-4_ikd-tree와_LIO의_지도_관리|04-4]] 2.2절에서 예고한 사실 — **ikd-Tree는 자체 rebuild 스레드를 돌린다.**

> **따라서 우리 노드가 SingleThreadedExecutor여도, 트리 입장에서는 항상 "메인 + rebuild" 2자 동시 접근 상태다.**

결정적으로, **ikd-Tree 자신이 내부에서 이 함수를 쓸 때는 반드시 락을 잡는다.**

```cpp
// ikd-Tree 자신의 rebuild 루틴
pthread_mutex_lock(&points_deleted_rebuild_mutex_lock);
flatten(*Rebuild_Ptr, Rebuild_PCL_Storage, MULTI_THREAD_REC);
```

**우리는 매초 아무 가드 없이 이 함수를 호출했다.**

```
   [우리 executor 스레드]                  [ikd-Tree rebuild 스레드]
        │ flatten(Root_Node)                     │
        │  ├─ Push_Down(root)  ← 쓰기            │ 서브트리 재구축 중
        │  ├─ left_son_ptr 따라감  ──────────────┼──► 그 포인터를 지금 갈아끼움
        │  └─ 이미 해제된 노드를 읽고/쓰기        │
        ▼                                        ▼
                     트리 손상 → 위치추정 붕괴 → 28 km
```

**손상된 것이 하필 [[04-4_ikd-tree와_LIO의_지도_관리|04-4]]가 말한 (A), 즉 위치추정에 실제로 쓰이는 지도**였다. [[08_사례연구_정지_상태_발산|08]]의 사고가 (B)만 건드렸던 것과 대조된다 — **그래서 훨씬 심각했다.**

### 3.5 왜 컨테이너 재생에서는 안 잡혔나

**경쟁 조건은 타이밍에 의존한다.**

| | 컨테이너(16코어 x86) | Jetson(6코어 A78) |
|---|---|---|
| rebuild 소요 시간 | 짧다 | 길다 |
| 평탄화와 겹칠 창 | 좁다 | 넓다 |
| 결과 | 677점, 완벽 | **28 km 발산** |

> **재생 검증만으로는 이런 결함을 잡을 수 없다.** [[08_사례연구_정지_상태_발산|08]] 7장에서 그토록 유용했던 재생 A/B가, 여기서는 **오히려 잘못된 안심을 줬다.**

### 3.6 부수적으로 밝혀진 것 — "지도가 사라졌다"의 정체

발산 직후 RViz에서 누적 지도가 사라진 것처럼 보였는데, 실제로는 지도 토픽에 **44,806점이 있었다.**

**지도가 지워진 게 아니라 28 km 밖으로 따라간 것이다.** 추정 위치가 튀자 지도 상자 이동 로직([[04-4_ikd-tree와_LIO의_지도_관리|04-4]] 3장 B)이 상자를 그쪽으로 옮기며 원래 방이 있던 영역을 삭제하고, 새 위치에 새 지도를 쌓고 있었다.

> **이것이 발산이 복구 불가능한 이유이기도 하다** — 돌아갈 기준이 되는 원래 지도가 트리에서 삭제되기 때문이다.

### 3.7 현재 방침

이 경로는 **기본 비활성이며 사용하지 않는다.** 코드에는 경고 주석과 함께 남겨 두었다. 되살리려면 **ikd-Tree 쪽에 락을 올바르게 잡는 스냅샷 API를 추가**해야 한다 — 필요한 가드(`Rebuild_Ptr`, `search_flag_mutex`)가 **private이라 외부에서는 올바르게 잠글 수 없다.**

> **API의 접근 제어가 스레드 안전성을 문서화하지 않는다.** 어떤 함수가 public이라는 것은 "외부에서 써도 된다"는 뜻이 **아니다.** 라이브러리가 자기 함수를 쓸 때 락을 잡는데 **그 락을 잡을 방법이 외부에 없다면, 그 함수는 사실상 내부용이다.**

## 4. 채택한 수정과 그 검증

### 4.1 수정: 누적 버퍼에 voxel 다운샘플

발행 직전에 5 cm 격자마다 점 하나만 남긴다.

**왜 맞는가**: 이건 사실 **ikd-tree가 원래 하던 중복 제거를 (B)에도 붙여준 것**이다. [[04-4_ikd-tree와_LIO의_지도_관리|04-4]]의 "크기가 시간이 아니라 공간에 비례한다"는 성질을 복원한다.

**기본값을 비활성(=upstream과 동일 동작)으로 두어**, 파라미터를 명시하지 않으면 기존 실험 결과와의 비교 가능성이 유지되게 했다.

### 4.2 검증: 증가 양상 자체가 바뀌었다

| 경과 | 수정 전 | 수정 후(voxel 0.05) |
|---|---|---|
| 60초 | 202,271점 / 9.7 MB | 30,121점 / 1.4 MB |
| 180초 | 612,742점 / 29.4 MB | 41,815점 / 2.0 MB |
| 300초 | 1,023,409점 / 49.1 MB | 45,413점 / 2.2 MB |
| 355초 | **1,212,001점 / 58.2 MB** | **46,678점 / 2.2 MB** |
| 증가율 | 3,412 pts/s | **131 pts/s** |

**선형(무한) → 포화**로 바뀌었다. 60초마다 증가폭이 대략 절반씩 줄어(+7,651 → +4,043 → +2,220 → +1,378) 약 4.7만 점으로 수렴한다. **정지된 장면의 5 cm 격자를 다 채우면 더 늘어날 곳이 없기 때문이다.**

| 지표 | 수정 전 | 수정 후 |
|---|---|---|
| CPU(CPU초/벽시계초) | 0.19 | **0.14** (지도 발행을 아예 끈 0.13과 사실상 동등) |
| 최악 지연 dt_max | 168ms | **129ms** |
| 누적오차 | 0.052 m | **0.052 m** (동일 — 정확도 손실 없음) |
| RSS 증가율 | 197 KB/s, 선형 증가 지속 | **62 KB/s, 약 155 MB에서 평탄화** |

**핵심**: 라이브 누적 지도와 저장 기능을 **유지한 채로**, 지도 발행을 포기한 것과 거의 같은 연산 비용을 얻었다.

**대가**: 저장/표시되는 지도 해상도가 5 cm로 제한된다. 다만 위치 추정용 ikd-tree는 이미 **50 cm**(`filter_size_map`)로 돌고 있어서, **우리가 보는 지도가 알고리즘이 쓰는 지도보다 여전히 10배 촘촘하다.**

> **선례가 있었다**: 이 프로젝트는 이전에 **똑같은 문제를 똑같은 방법으로** 이미 한 번 해결한 적이 있다(자체 누적 버퍼가 300만 점까지 커지던 것을 5 cm voxel로 5~6만 점에서 안정화). **같은 병에 같은 약이다** — 과거 기록을 뒤지는 것이 새 해법을 발명하는 것보다 빠를 때가 많다.

## 5. 채택하지 않은 대안들 — 왜 안 했는지도 기록한다

| 대안 | 장점 | 안 한 이유 |
|---|---|---|
| **ikd-tree 스냅샷으로 되돌리기** | 별도 버퍼가 아예 불필요. 가장 구조적으로 깔끔 | **경쟁 조건으로 28km 발산(3장). 사용 금지** |
| **MultiThreadedExecutor + 콜백 그룹 분리** | 지도 복사가 아무리 커져도 EKF를 못 막음. 근본 방어 | upstream 구조 변경. 버퍼를 두 스레드가 만지므로 스레드 안전성 검토 필요 — **후속 작업으로 남김** |
| **발행 주기 늘리기**(1Hz → 0.2Hz) | 한 줄 수정 | 비용이 여전히 시간에 비례. **시점을 늦출 뿐** |
| **`dense_publish_en: false`** | 코드 수정 없이 config만. CPU 동등 | 누적 소스가 50 cm 다운샘플 스캔이 돼 **지도가 훨씬 거칠어짐** |
| **`map_en: false`** | 발산은 사라짐. CPU 최소 | **라이브 지도 뷰와 저장 기능이 동시에 죽는다**(6장) |
| **구독자 없으면 발행 생략** | 실측 CPU 0.19 → 0.131 | 한 번 채택했다가 **철회**(7장) |

## 6. `map_en: false`를 쓸 수 없는 이유 — 정정된 판단

초기 문서들은 이 옵션을 **"위험 낮은 1순위 완화책"**으로 제시했다. **부정확했고, 코드를 재확인해 바로잡았다.**

```
이 스위치가 게이트하는 범위:

  ikd-tree 갱신  ← 실제 위치추정에 쓰이는 지도
      → 이 스위치와 **무관하게** 매 프레임 항상 호출됨
      ⇒ 위치추정 정확도에는 영향을 주지 않는다  ✔ 맞음

  누적 버퍼  ← 문제의 무한 누적 버퍼
      → 지도 발행 함수 안에서만 채워짐
      → 그 함수는 이 스위치가 true일 때만 호출됨
      ⇒ false면 이 버퍼가 영구히 빈 상태로 남는다
         ├─ 라이브 지도 토픽의 **유일한** 데이터 소스
         └─ 저장 서비스가 저장하는 **유일한** 소스
      ⇒ 라이브 지도 뷰와 PCD 내보내기가 **동시에 완전히 무력화**
```

**발산과 정확히 같은 코드 경로를 공유하기 때문에 "발산만 없애고 나머지는 그대로"가 불가능하다.** "위험이 낮은 완화책"이 아니라 **명백한 트레이드오프**다.

> **교훈**: "이 스위치는 publish 여부만 바꾸니 안전하다"는 판단은 **의존관계를 끝까지 따라가 보지 않은 추측**이었다. 스위치 하나가 무엇을 게이트하는지는 코드로 확인해야 한다 — 그 변수의 **모든 사용처**를 grep으로 세는 데 몇 분이면 된다.

## 7. 구독자 가드를 철회한 이유 — 좋은 아이디어도 조합에 따라 위험해진다

"구독자가 없으면 직렬화·발행을 건너뛴다"는 가드를 넣었다가 **철회했다.** 실측 효과는 분명 있었다(CPU 0.19 → 0.131). 철회 이유는 네 가지다.

1. voxel을 켜면 메시지가 2.2 MB로 줄어 직렬화 비용이 이미 미미하다. **두 수정의 CPU 절감이 겹친다.**
2. 구독자가 없으면 DDS가 네트워크로 보내지도 않으므로 남는 건 로컬 복사뿐이다.
3. 정작 **지도를 보는 순간(구독자 있음)에는 가드가 무력화**되어 도움이 안 된다.
4. **voxel 없이 가드만 있으면 오히려 위험하다.** 가드는 발행만 막고 누적은 막지 않으므로, 아무도 안 보는 동안 버퍼는 계속 쌓인다. 한참 뒤 RViz를 여는 순간 수백 MB를 매초 직렬화하게 되어 **즉시 터진다.** 실패를 **"보는 순간 터지는" 관측자 의존적 형태**로 바꿔놓는 셈이라, 일관된 실패보다 나쁘다.

참고로 앞서 언급한 포크에는 이 가드가 포함돼 있지만, 그쪽은 voxel·중복추가 방지와 **함께** 들어간 것이라 **단독으로 떼어오면 의미가 달라진다.**

> **교훈**: 개별로 측정하면 좋아 보이는 수정이, 조합에서는 중복이거나 심지어 해로울 수 있다. 그리고 **"실패를 눈에 덜 띄게 만드는 수정"은 개선이 아닐 수 있다.**

## 8. 진단 관점

| 증상 | 확인 순서 |
|---|---|
| 개발 PC에서는 완벽한데 실기체에서만 파국적 실패 | **경쟁 조건을 의심한다.** 코어를 줄이거나 CPU 부하를 주입해 재현을 시도(3.5절) |
| 발산 후 지도가 "사라진" 것처럼 보임 | 지워진 게 아니라 **추정 위치를 따라 멀리 이동**한 것일 수 있다. 점 개수를 실제로 세어 본다(3.6절) |
| 라이브러리 함수를 썼는데 간헐적으로 이상 동작 | 그 라이브러리가 **내부 스레드를 돌리는지** 소스에서 `pthread_create`/`std::thread`를 grep(3.4절) |
| "이 플래그만 끄면 안전하다"고 판단하려 할 때 | 그 변수의 **모든 사용처**를 grep으로 센다. 예상보다 많은 것을 게이트하는 경우가 흔하다(6장) |
| 어떤 수정이 CPU를 낮췄을 때 | **다른 수정과 함께 켠 상태에서 다시 측정한다.** 효과는 더해지지 않는다(7장) |
| upstream 저장소를 신뢰할지 판단할 때 | **출처의 신뢰성**과 **유지보수 활동**을 따로 본다. 스타 수는 후자의 지표가 아니다(2.5절) |

## 9. 이해도 점검

1. "우리 노드는 SingleThreadedExecutor이니 ikd-tree에 동시 접근이 없다"는 추론의 어디가 틀렸는가?
2. 어떤 라이브러리 함수가 `public`이다. 이것은 "외부에서 호출해도 스레드 안전하다"는 뜻인가?
3. 컨테이너 재생 검증을 통과한 수정이 실기체에서 28km 발산을 냈다. 재생 검증이 쓸모없다는 뜻인가?
4. ROS1에서 지도 발행이 `if(0)`으로 꺼져 있었다. 포팅한 사람이 이를 켠 것은 잘못인가?
5. "구독자가 없으면 발행을 건너뛴다"는 가드는 CPU를 확실히 줄였는데 왜 철회했는가?

> [!info]- 정답 및 해설 보기
> 1. **executor는 우리 콜백만 관리한다.** ikd-Tree는 **자체 rebuild 스레드**를 따로 돌리므로, 트리 입장에서는 언제나 "메인 + rebuild" 2자 동시 접근이다. 우리 쪽이 싱글 스레드라는 사실은 **트리의 동시성과 아무 상관이 없다.** 확인 방법은 간단하다 — 라이브러리 소스에서 스레드 생성을 grep한다.
> 2. **아니다.** 접근 제어(public/private)는 **가시성**을 말할 뿐 **스레드 안전성 계약을 문서화하지 않는다.** 이 사례에서 평탄화 함수는 public이지만, ikd-Tree 자신이 내부에서 호출할 때는 반드시 뮤텍스를 잡는다. **그 뮤텍스가 private이라 외부에서는 올바르게 잠글 수 없다면, 그 함수는 사실상 내부용**이다. 게다가 이름과 달리 읽기가 아니라 노드를 **수정**하는 함수였다.
> 3. **아니다. 두 종류의 검증이 각각 다른 것을 잡는다.** 재생 검증은 **로직 버그**에 강하고 **타이밍 버그**에 무력하다. 실제로 [[08_사례연구_정지_상태_발산\|08]]에서는 재생이 결정적 증거를 줬다. 경쟁 조건을 노리려면 **의도적으로 자원을 줄여야 한다** — 코어 제한, CPU 부하 주입, 저사양 실기. 재생 검증을 버리는 게 아니라 **한 종류를 더 추가**하는 것이 답이다.
> 4. **동기는 정당했다.** 사용자 입장에서 빈 토픽은 "고장난 기능"으로 보인다. 문제는 켠 것 자체가 아니라, **원래 코드가 보장하던 성질을 함께 옮기지 않은 것**이다 — ①출처가 자기 관리되는 자료구조 ②매번 clear ③기본 비활성, 세 가지가 전부 사라졌다. 포팅은 코드가 아니라 **"왜 그렇게 했는가"를 옮기는 일**이다.
> 5. 네 가지 이유가 있는데, 가장 중요한 것은 넷째다. **가드는 발행만 막고 누적은 막지 않는다.** 그래서 아무도 안 보는 동안 버퍼는 계속 쌓이고, 한참 뒤 RViz를 여는 순간 수백 MB를 매초 직렬화하며 **즉시 터진다.** 즉 실패를 **"관측하는 순간 터지는" 형태**로 바꿔놓는데, 이는 일관된 실패보다 나쁘다. 나머지는 voxel 수정과 효과가 겹치고, 정작 지도를 볼 때는 무력화된다는 점이다. **"실패를 눈에 덜 띄게 만드는 수정"은 개선이 아닐 수 있다.**
