## 1. 개요

결론부터 한 줄로 적으면 이렇다.

> **LiDAR를 책상에 가만히 놔둬도 추정 위치가 수백 m로 튀던 문제의 원인은, "지도를 화면에 보여주는 방식"이 지워지지 않는 점 더미를 만들었고, 그 더미 전체를 매초 복사하느라 위치 계산이 굶어 죽은 것이다. 센서도, 파라미터도, 알고리즘도 멀쩡했다.**

하지만 **결론을 먼저 아는 것은 학습에 별로 도움이 안 된다.** 이 문서의 가치는 답이 아니라 **어떻게 거기까지 갔는가**에 있다. 순서대로 따라가 보자.

## 2. 증상 — 무엇을 보았나

| 시점 | 관측 | 관측자 |
|---|---|---|
| 초기 | 정지 상태 `/Odometry`가 원점 근방 수 mm~1cm. **완전히 정상** | 짧은 구간 실측 |
| +1일 | 책상에 정지시켜 뒀는데 **TF가 미세하게 흔들린다.** "지도는 정상인데 tf만 흔들린다" | 사용자 |
| +3일 | `map_en:false` 인스턴스는 14분+ 생존. `map_en:true`는 **세 번 모두 5~6분에 크래시 로그 없이 스스로 죽었다** | 관찰(n=3) |
| +4일 | 손에 들고 걸어다니면 추정 위치가 갑자기 멀리 튄다(발산). 반복 발생 | 사용자 |
| +4일 | 정지 대조군 bag 4개 **전부에서 발산 관측**. 최종 **307.3 m** | bag 실측 |
| +5일 | (수정 시도 후) **28 km** 발산 | Jetson 실기 — [[09_사례연구_28km_발산과_ROS2_포팅_회귀\|09]] |

**이 목록 자체가 첫 번째 교훈이다.** 같은 근본 원인이 "미세한 흔들림", "조용한 프로세스 사망", "파국적 발산"이라는 **완전히 달라 보이는 세 가지 증상**으로 나타났다. 처음엔 이것들이 같은 문제인지조차 몰랐다.

그리고 직관에 반하는 관측이 하나 있었다.

> **가만히 있을 때 더 나빴다.** "빠르게 움직여서 발산했나?" 하고 의심하는 것이 자연스러운데, 실제로는 **정지 상태가 가장 위험했다.** 이 관측이 나중에 원인을 특정하는 결정적 단서가 된다.

## 3. 1차 조사 — 증거 없이 가설만 세운 단계

이 시점에 센서 이더넷 링크가 끊겨 있어 **실측을 전혀 할 수 없었다.** 그래서 코드와 설정만 읽고 가설 7개를 세웠다.

이 프로젝트의 진단 규칙에 따라 **모든 가설에 신뢰도를 붙였다.**

| 가설 | 내용 | 당시 신뢰도 |
|---|---|---|
| **A** | `map_en:true`로 무한히 커지는 시각화 버퍼가 EKF를 지연/발산시킨다 | 보통 |
| B | 온라인 외부보정(`extrinsic_est_en:true`)이 정지 상태에서 잡음을 유입시킨다 | 보통 |
| C | 좁은 공간의 기하학적 단순성(degeneracy) | 보통 |
| D | 진동 주파수가 IMU 샘플레이트 근처와 겹침 | 낮음 |
| E | IMU 초기화 구간의 잔여 영향 | 낮음 |
| F | Mid-360S IMU 노이즈 특성과 공용 기본 covariance의 불일치 | 낮음 |
| G | **순수 물리적 진동(책상 흔들림 등, 소프트웨어 무관)** | 낮음 |

**가설 A를 1순위로 올린 근거 두 가지**

1. **외부 근거**: FAST-LIO 저장소 issue #449가 **우리와 정확히 같은 스택**(Ubuntu 22.04 + ROS2 Humble + Mid-360S + `map_en:true`)에서 같은 증상을 보고했다. 시각화 버퍼가 7,836점 → 595,729점으로 늘고, 직렬화 시간이 0.010초 → **1.511초**로 커지며, EKF 타이머가 1.34초씩 밀리고, 속도 추정이 **1,000 m/s대**로 발산했다는 로그까지 첨부되어 있었다.
2. **독립 확인**: 우리 소스에서 그 버퍼가 매번 누적만 하고 **비우는 코드가 저장소 전체에 없다**는 것을 직접 grep으로 확인했다.

> **여기서 배울 점 둘.**
>
> 외부 이슈를 그대로 믿지 않고, **우리 코드에 그 전제 조건이 실제로 존재하는지 독립적으로 확인**했다. 그리고 그 이슈가 **유지보수자 코멘트 하나 없이 stale 봇에 의해 닫혔다**는 사실을 신뢰도에 반영했다 — "누가 보고했다"는 "확인됐다"가 아니다.
>
> 반대로, **가설 G(그냥 책상이 흔들린 것)를 목록에 남겨 둔 것도 중요하다.** "소프트웨어 문제일 것"이라는 전제 자체가 하나의 가설이다.

## 4. 결정적 개념: "지도"가 두 가지를 가리키고 있었다

조사가 풀리기 시작한 지점이 여기다.

[[04-4_ikd-tree와_LIO의_지도_관리|04-4]] 5장에서 정리한 대로, FAST-LIO 안에는 성격이 완전히 다른 지도가 둘 있다 — **(A) 알고리즘이 쓰는 ikd-tree**와 **(B) 사람이 보는 시각화 버퍼**다.

> **이번 문제는 전적으로 (B)에서 생겼다. (A)는 처음부터 끝까지 정상이었다.**

그래서 사용자의 최초 보고 — **"지도는 정상인데 tf만 흔들린다"** — 가 나온 것이다. **이 한마디가 사실은 가장 정확한 관측이었는데, 당시엔 그것이 얼마나 중요한 단서인지 아무도 몰랐다.**

> **학습 포인트**: 같은 단어가 시스템 안에서 두 개의 다른 것을 가리키면, 그 애매함이 **관측을 잘못 해석하게 만든다.** 용어를 분리하는 것만으로 문제가 반쯤 풀린다.

## 5. 2차 조사 — bag 실측으로 메커니즘을 특정하다

사용자가 정지 대조군 bag 4개를 기록했고, **4개 전부에서 발산이 관측됐다.** 이제 데이터가 있다.

### 5.1 무엇을 측정했나

`/Odometry`만 파싱해서 두 가지를 봤다.

- **원점거리** — 정지 bag이므로 참값이 "원점 고정"이다. **원점거리가 곧 오차**가 된다. 참값을 공짜로 얻는 영리한 설계다.
- **발행 간격 dt** — 프레임과 프레임 사이 시간. **EKF가 굶주렸는지 보는 지표**다.

### 5.2 결과 1: dt가 경과 시간에 비례해 커진다

| bag | 길이 | dt 최댓값 추이 |
|---|---|---|
| control | 293초 | 0-30s **121.8ms** → 210-240s 387.6ms → 270-300s **1994.3ms** |
| control2 | 177초 | 0-30s 190.3ms → 120-150s 496.4ms → 150-180s **2376.7ms** |
| control3 | 350초 | 0-10s 130.6ms → 170-180s 711.9ms → 340-350s **930.5ms** |
| cpu_load | 117초 | 80-90s 837.5ms → 90-100s **1713.8ms** → 100-110s 1886.2ms |

**정상 발행 간격은 10ms(100Hz 타이머)다.** 2초짜리 지연이 나온다는 것은 **EKF가 200프레임 분량을 통째로 못 돌았다**는 뜻이다.

### 5.3 결과 2: 지연이 정확히 1초 주기로 반복된다

control3의 특정 구간을 프레임 단위로 펼치면:

```
[2934] rel_t=293.394s  dt_prev=  11.8ms
[2935] rel_t=293.490s  dt_prev=  96.4ms
[2936] rel_t=294.314s  dt_prev= 824.0ms   ← 대형 지연
[2937]~[2943]          dt_prev=   9~10ms  (정상)
[2945] rel_t=294.493s  dt_prev=  98.6ms
[2946] rel_t=295.315s  dt_prev= 821.6ms   ← 다음 주기
...
[2966] rel_t=297.386s  dt_prev= 895.8ms
```

**약 9개 프레임이 정상으로 오다가, 매 주기 끝에 800~900ms 지연이 한 번씩 발생한다. 그 주기가 정확히 1초다.**

그리고 코드에는 1초 주기 타이머가 하나 있다.

```cpp
auto period_ms     = milliseconds(1000.0/100.0);  //   10ms → EKF 타이머
auto map_period_ms = milliseconds(1000.0);        // 1000ms → 지도 발행 타이머
```

> **주기가 일치한다는 것은 강력한 증거다.** 우연히 1초마다 다른 이유로 멈출 확률은 매우 낮다. 이런 **주기성 대조**는 원인 후보를 좁히는 가장 값싼 방법 중 하나다.

### 5.4 결과 3: 지연 직후에 위치가 튄다 — 인과의 방향

`cpu_load` bag의 발산 순간:

```
[1085] rel_t=108.845s  dist= 8.615m  dt_prev=   9.9ms
[1086] rel_t=109.730s  dist= 8.614m  dt_prev= 885.6ms   ← 885ms 정지
[1087] rel_t=109.740s  dist= 8.612m  dt_prev=   9.8ms
[1088] rel_t=109.755s  dist=16.977m  dt_prev=  15.0ms   ← 한 프레임에 8m 점프
```

**885ms 멈춘 바로 다음 프레임에서 8m가 튀었다.** 이후 계속 발산해 bag 종료 시점(117.3초)에 **307.3 m**에 도달했다.

이것이 "대형 지연 → 발산"이라는 **인과 방향을 시사하는 가장 직접적인 증거**였다. 상관만으로는 "발산 때문에 느려진 것"일 수도 있는데, **시간 순서가 방향을 알려준다.**

### 5.5 왜 지연이 발산을 만드는가

```
정상:  IMU 예측(10ms) → LiDAR 보정 → IMU 예측 → LiDAR 보정 → ...
       오차가 계속 작게 유지된다

지연:  IMU 예측 ────────── 900ms 동안 보정 없음 ──────────→ LiDAR 보정
                (IMU만으로 홀로 추측. 가속도 이중적분 오차가 급격히 쌓임)
                                                              │
                                                              ▼
                                        어긋난 위치를 기준으로 매칭 시도
                                               → 엉뚱한 평면에 맞춰버림
                                               → 잘못된 위치로 지도에 점 추가
                                               → 오염된 지도에 다시 맞춤
                                               → 악순환(발산)
```

[[04-3_FAST-LIO2_알고리즘_구조|04-3]] 6장의 point-to-plane 매칭은 **"현재 추정이 대충은 맞다"를 전제**한다. 초기 추정이 크게 틀리면 완전히 다른 평면에 대응시켜 버리고, 그 결과가 지도에 기록되면서 **되돌아올 수 없게 된다.**

## 6. 3단 인과 — 각각은 사소해 보이는 세 가지

**세 가지가 겹쳐야 사고가 난다.** 하나씩 보면 전부 "그럴 수도 있지" 수준이다.

### 6.1 1단계: 점 더미가 시간에 비례해 무한히 커진다

시각화 버퍼(B)는 매번 현재 스캔을 **그냥 계속 더한다.** [[04-4_ikd-tree와_LIO의_지도_관리|04-4]] 3장에서 본 **자기 관리 장치가 하나도 없다** — 중복 제거도, 공간 정리도, 비우는 코드도 없다.

**실측(정지 상태, 355초 재생)**:

| 경과 | 점 개수 | 메시지 크기 |
|---|---|---|
| 30초 | 99,282 | 4.8 MB |
| 120초 | 407,538 | 19.6 MB |
| 240초 | 825,089 | 39.6 MB |
| 355초 | **1,212,001** | **58.2 MB** |

**초당 3,412점, 0.164 MB씩 딱 선형으로 증가한다. 상한이 없다.**

| 가동 시간 | 매초 직렬화·발행되는 크기 |
|---|---|
| 5분 | 49 MB |
| 10분 | 98 MB |
| 30분 | 295 MB |
| 60분 | 590 MB |

> **왜 점 하나가 48바이트인가**: 포인트 타입이 좌표+intensity 말고도 **normal 벡터와 curvature까지** 싣는 구조체다. 누적 지도를 보는 데는 전혀 필요 없는 값인데 메모리를 3배 쓴다(좌표+intensity만이면 16바이트). 실측 증가율 0.164 MB/s ÷ 48 B = 3,412 points/s로 정확히 맞는다 — **숫자가 서로 맞아떨어지는지 확인하는 것**이 가설 검증의 기본이다.

### 6.2 2단계: 그 더미 전체를 1초마다 통째로 복사한다

메시지로 만드는 함수는 **더미 전체를 훑어 새 버퍼에 복사**한다. 비용이 크기에 정비례한다. 5분이면 매초 49 MB 복사, 30분이면 매초 295 MB 복사다. 게다가 그때마다 그 크기만큼 메모리를 새로 할당했다 해제한다.

RSS 실측에서 그 순간이 실제로 잡혔다 — 특정 샘플에서 RSS가 201 MB에서 **266.7 MB로 튀었다가** 다시 201 MB로 돌아왔다. 그 시점 버퍼 크기(약 49 MB)의 메시지를 새로 할당하는 순간이 포착된 것이다.

### 6.3 3단계: 그 복사가 위치 계산과 같은 스레드에서 일어난다

노드는 인자 없는 `rclcpp::spin()`으로 돌고 있었다. 이는 **SingleThreadedExecutor**이며, 콜백을 **한 번에 하나씩** 실행한다([[06_Composable_Node와_Executor_구조|응용 06]]에서 다룬 바로 그 구조다).

```
   [단일 executor 스레드]
   ├─ EKF 타이머 (10ms 주기)        ┐
   └─ 지도 발행 타이머 (1s 주기)     ┘  둘이 같은 스레드를 나눠 쓴다

   시간 →
   ██ ██ ██ ██ ██ ████████████████████████████ ██ ██ ██ ██
   EKF                  지도 복사 (58MB)         EKF
                        ← 이 동안 EKF는 줄만 선다 →
```

**지도 복사가 58 MB를 처리하는 동안 EKF 콜백은 아예 실행되지 못한다.** 5.3절에서 본 800~900ms 지연이 정확히 이 모양이다.

> **여기가 이 사례의 핵심이다.** 두 콜백은 **서로를 호출하지 않는다.** 코드의 호출 그래프만 봐서는 아무 관계가 없다. 그런데 **같은 스레드라는 자원을 공유**한다. **자원 공유는 코드에 안 나타난다.**

### 6.4 왜 "가만히 있을수록 더 나빠지는가" — 직관과 반대인 이유

이제 2장의 그 이상한 관측을 설명할 수 있다.

| | 가만히 있을 때 |
|---|---|
| **ikd-tree (A)** | 새 기하 정보가 없으니 격자 중복 제거에 다 걸린다 → **더 이상 안 커진다** |
| **시각화 버퍼 (B)** | 중복 제거가 없으니 **같은 벽을 1초에 한 번씩 영원히 다시 쌓는다** → 계속 커진다 |

> **이 누적 방식은 ikd-tree가 가장 잘 하는 상황(정지)에서 가장 못한다.**

## 7. 결정적 실험: 재생(replay) 기반 A/B

여기가 조사 설계의 백미다. 가설이 아니라 **실험 설계**를 보자.

### 7.1 핵심 아이디어

bag에 **원본 센서 토픽**이 들어 있으므로, 같은 입력에 **config만 바꿔** 다시 돌릴 수 있다. 즉 **하드웨어 없이, 사용자 없이, 몇 번이고 반복 가능한 테스트베드**가 생긴다.

이 설계를 가능하게 한 **사전 결정**이 하나 있었다. bag 기록 도구를 만들 때 **누적 지도 토픽을 의도적으로 제외하고 원본 센서 토픽을 기록하기로** 한 것이다. 이유는 "무한 누적이라 용량이 크고, 원본으로 재생하면 어차피 재생성된다"였는데, 결과적으로 **A/B 실험 가능성 자체를 확보한 결정**이 됐다.

> **교훈**: 무엇을 기록할지 정하는 것은 나중에 **무엇을 조사할 수 있는지**를 정하는 일이다.

### 7.2 실험 위생(hygiene) — 이것도 그대로 배울 가치가 있다

| 조치 | 왜 |
|---|---|
| `ros2 launch` 대신 설치된 바이너리를 직접 실행 | PID 추적과 CPU 시간 측정 정확도 |
| 재생을 원본 센서 토픽으로만 제한 | bag 안의 `/Odometry`/`/tf`가 재생돼 **노드 출력과 충돌하는 것**을 방지 |
| `taskset`으로 코어 제한 | Jetson의 연산 제약을 흉내 |
| 실험 전용 `ROS_DOMAIN_ID` | 로봇/드론 도메인과 격리 |
| 궤적은 **message header stamp**, 지연은 **수신 시각** 기준 | 두 시간축을 섞으면 재생 배속이 결과를 오염시킨다 |
| config 변형을 스크립트가 **한두 줄씩만** 생성 | 어느 줄이 왜 달라졌는지가 스크립트에 남는다 |
| 시행마다 **노드를 새로 띄운다** | 누적 버퍼가 매번 0에서 시작해야 시행이 서로 독립이 된다 |

**타당성 확인**: baseline 재생에서 `/Odometry` 메시지 수가 원본과 **1,169개로 완전히 일치**했다(스캔 누락 없음). **이 확인 없이 결과를 믿으면 안 된다.**

### 7.3 그리고 충격적인 결과가 나왔다

| bag | Jetson 원본 | 컨테이너 재생 |
|---|---|---|
| cpu_load(117초) | **307.3 m 발산**, dt max 1886ms | **0.064 m**, 발산 없음, dt max 108ms |
| control3(350초) | **2.81 m drift**, dt max 930ms | **0.049 m**, 증가 추세 없음, dt max 160ms |

**같은 데이터, 같은 config, 같은 코드인데 결과가 완전히 다르다.** CPU를 1코어로 묶어도 0.064 m로 동일했다.

control3 재생의 구간별 누적오차는 60초 0.039 m → 180초 0.028 m → 300초 0.023 m로, **시간이 지나도 커지지 않는다**(추세 없이 3~5 cm에서 진동).

> **결론: 발산의 원인은 센서 데이터도, 환경 기하도, 파라미터도 아니라 실행 환경의 연산 여력이다.**

이 결과가 실험의 방향 자체를 바꿨다. 원래 목표는 "drift를 줄이는 파라미터 찾기"였는데, **줄일 drift가 애초에 없었다.** 그래서 주 평가 지표를 **"누적오차"에서 "CPU 비용"으로 옮겼다.**

> **재현 실패도 데이터다.** 컨테이너가 발산을 **재현하지 못한 것** 자체가 "원인은 데이터가 아니라 연산 여력"이라는 결정적 증거가 됐다.

### 7.4 파라미터 A/B 11종의 결론

| config | 변경점 | 최대오차(m) | dt_max | CPU |
|---|---|---|---|---|
| baseline(2코어) | — | 0.052 | 168ms | 0.19 |
| v1_ext_off | `extrinsic_est_en:false` | 0.063 | 138ms | — |
| v3_voxel02_pf2 | filter 0.2 + `point_filter_num` 2 | **0.027** | 175ms | — |
| v4_tuned | v3 + iter5 + ext_off | **0.026** | 224ms | 0.28 |
| v7_base_nomap | baseline + `map_en:false` | 0.049 | 227ms | **0.13** |
| v8_nodense | `dense_publish_en:false` | 0.049 | 122ms | **0.14** |
| **v10_mapvoxel** | baseline + **voxel 0.05** | 0.052 | **129ms** | **0.14** |
| **v11_tuned_mapvoxel** | v4_tuned + voxel 0.05 | **0.027** | **130ms** | 0.21 |

(CPU는 CPU초/벽시계초. 1.0 = 코어 1개 상당)

- **전 config가 1.4~6.3 cm 대역.** 설정으로 줄일 drift가 거의 없다.
- `extrinsic_est_en:false`(v1) 단독은 **오히려 근소하게 나빴다.** 외부 조사가 흔히 권고하는 항목인데도 이 정지 데이터에서는 개선 근거가 없었다. 다만 차이가 1~2 cm라 노이즈와 구분하기 어려워 **단정하지 않는다.**
- **의미 있는 차이는 CPU에서만 나타났다.**

> **학습 포인트**: 외부 권고(README, 커뮤니티 config)가 **우리 조건에서는 틀릴 수 있다. 실측이 권고를 이긴다.** 다만 "차이가 노이즈 수준이라 단정하지 않는다"고 명시한 것도 똑같이 중요하다 — 실측을 근거로 과신하는 것도 같은 종류의 실수다.

## 8. 메모리는 원인이 아니었다 — 반증도 기록한다

"5~6분에 크래시 로그 없이 죽은 것이 OOM 아닌가"라는 경쟁 가설을 RSS 실측으로 확인했다.

- 문제가 관측된 5~6분 시점의 RSS는 **약 200 MB**에 불과했다.
- Jetson은 7.6 GB 중 **available 4.76 GB**였다. **OOM과는 거리가 멀다.**
- 따라서 원인은 **CPU/직렬화 시간**이라는 결론이 유지된다.

> **가설을 지지하는 증거만이 아니라, 경쟁 가설을 배제하는 증거도 남긴다.** 이것이 없으면 나중에 같은 질문이 다시 올라온다.

## 9. 진단 관점

| 증상 | 확인 순서 |
|---|---|
| 정지 상태인데 시간이 갈수록 위치가 나빠짐 | **시간에 비례해 커지는 무언가**를 찾는다. 지도 토픽 메시지 크기를 시간에 따라 기록해 본다 |
| `/Odometry` 발행 간격이 들쭉날쭉 | dt를 시계열로 뽑는다. **주기적 대형 지연이면 다른 콜백과의 스레드 경합**을 의심(6.3절) |
| 노드가 크래시 로그 없이 죽음 | RSS를 먼저 재서 OOM을 **배제**한다(8장). 배제되면 연산 쪽 |
| 실기체에서만 발산, 개발 PC에서는 재현 안 됨 | **연산 여력 차이**를 의심한다. `taskset`으로 코어를 줄여 재현을 시도 |
| "지도는 정상인데 tf만 이상하다" | **두 개의 지도**([[04-4_ikd-tree와_LIO의_지도_관리\|04-4]] 5장) 중 어느 쪽을 말하는지 먼저 확정한다 |
| 파라미터를 아무리 바꿔도 개선이 없음 | **파라미터가 원인이 아닐 가능성**을 진지하게 본다. 원인이 다른 계층(연산 자원, 스레드)에 있을 수 있다 |

## 10. 이해도 점검

1. 정지 상태가 이동 상태보다 더 위험했던 이유는?
2. dt(발행 간격) 지연이 **정확히 1초 주기**로 반복된다는 관측이 왜 강력한 증거인가?
3. 컨테이너 재생에서 발산이 **재현되지 않은 것**은 조사의 실패인가?
4. EKF 콜백과 지도 발행 콜백은 서로를 호출하지 않는다. 그런데도 한쪽이 다른 쪽을 막을 수 있는 이유는?
5. `map_en:false`로 두면 발산이 사라진다. 이것을 "위험 없는 해결책"이라고 말할 수 있는가?

> [!info]- 정답 및 해설 보기
> 1. 두 지도가 **정반대로 반응**하기 때문이다. **ikd-tree(A)**는 새 기하 정보가 없으면 격자 중복 제거에 다 걸려 **더 이상 안 커진다**. 반면 **시각화 버퍼(B)**는 중복 제거가 없어서 **같은 벽을 1초마다 영원히 다시 쌓는다.** 즉 이 누적 방식은 ikd-tree가 가장 잘 하는 상황에서 가장 못한다. 이동 중에는 오히려 새 공간이 계속 들어와 상대적으로 덜 두드러졌다.
> 2. **코드에 정확히 1초 주기 타이머가 하나 있기 때문**이고, 우연히 1초마다 다른 이유로 멈출 확률이 매우 낮기 때문이다. 이런 **주기성 대조**는 "무엇이 이 지연을 만드는가"의 후보를 단번에 좁힌다. 관측된 주기와 코드의 주기가 일치하면 그것은 상관이 아니라 거의 지목이다.
> 3. **아니다. 그 자체가 결정적 증거였다.** 같은 데이터·같은 config·같은 코드로 재현이 안 됐다는 것은 **원인이 데이터·환경 기하·파라미터가 아니라 실행 환경(연산 여력)에 있다**는 뜻이다. 이 결과가 조사 방향을 "drift 줄이는 파라미터 찾기"에서 "CPU 비용 줄이기"로 바꿨다. **재현 실패도 데이터다.**
> 4. **같은 스레드라는 자원을 공유**하기 때문이다. `rclcpp::spin()`은 SingleThreadedExecutor라 콜백을 한 번에 하나씩만 실행하므로, 무거운 콜백이 도는 동안 다른 콜백은 줄을 선다. 핵심은 **이 관계가 코드의 호출 그래프에 나타나지 않는다**는 것이다 — 자원 공유는 호출 관계로 드러나지 않으므로, 코드를 읽는 것만으로는 못 찾는다.
> 5. **말할 수 없다.** 그 스위치는 발산의 원인인 버퍼를 게이트하지만, **동시에 라이브 지도 뷰와 PCD 내보내기의 유일한 데이터 소스도 죽인다.** 즉 "발산만 없애고 나머지는 그대로"가 불가능한 **명백한 트레이드오프**다. 자세한 의존관계 추적은 [[09_사례연구_28km_발산과_ROS2_포팅_회귀\|09]] 6장에 있다. 일반화하면 — **"이 플래그는 X만 끈다"는 코드로 확인하기 전까지 가설이다.**
