## 1. 개요

00에서 짚은 "6자유도"와 "바퀴 오도메트리 부재"가 실제로 좌표계와 상태 추정을 어떻게 바꾸는지 구체적으로 정리한다. 01에서 배운 `map → odom → base_footprint` 구조가 드론에서 어떻게 달라지는지가 핵심이다.

## 2. 핵심 개념: 좌표계 구조의 변화

### 2.1 `base_footprint`가 사라진다

지상로봇의 TF 트리에는 `base_link`(로봇 몸체 중심, 높이 포함)와 `base_footprint`(바닥에 투영한 점, z=0)가 함께 존재했다. Nav2의 2D 내비게이션이 후자를 기준으로 계산했기 때문이다.

**드론에는 `base_footprint`가 없다.** "바닥에 투영한다"는 개념 자체가 성립하지 않고, z(고도)가 제어해야 할 실제 상태값이기 때문이다. 드론의 TF는 `map → odom → base_link`로 끝난다.

```text
[지상로봇]  map → odom → base_footprint → base_link → (센서들)
[드론]      map → odom → base_link → (센서들)
```

### 2.2 FLU와 NED — 두 가지 좌표 관례의 충돌

ROS와 비행 컨트롤러(PX4)는 **서로 다른 좌표 관례**를 쓴다. 이것이 드론 개발에서 가장 흔한 혼란의 원인이다.

| 관례 | 축 방향 | 쓰는 곳 |
|---|---|---|
| **FLU / ENU** | x=전방(Front), y=좌(Left), z=상(Up) | ROS 표준([REP103](https://www.ros.org/reps/rep-0103.html)), 모든 ROS 노드 |
| **FRD / NED** | x=전방(Front), y=우(Right), z=하(Down) | PX4 내부, 항공 분야 관례 |

**z축 부호가 반대**라는 점이 특히 중요하다 — ROS에서 "위로 2m"는 `z=+2`이지만 PX4 내부에서는 `z=-2`다. PX4의 ROS2 브릿지는 이 변환을 자동 처리해주지만, 직접 좌표를 다룰 때는 어느 관례인지 항상 확인해야 한다.

### 2.3 IMU의 위상이 달라진다

지상로봇에서 IMU는 "바퀴 오도메트리를 보조하는" 센서였다. 드론에서 IMU는 다음 두 가지를 **동시에** 담당하는 1차 센서다.

1. **자세 제어의 기준** — 비행 컨트롤러가 초당 수백~수천 번 IMU를 읽어 기울기를 계산하고 모터를 조절한다. 이게 없으면 즉시 추락한다.
2. **위치 추정의 기반** — 바퀴가 없으므로 VIO가 IMU + 카메라만으로 위치를 추정해야 한다.

그래서 드론에서는 **IMU 데이터의 주기와 품질이 지상로봇보다 훨씬 중요하다.** D 시리즈에서 다룬 "D435i IMU가 공장 미보정 상태"라는 문제(01-5, 02-7)가 드론에서 훨씬 치명적으로 작용하는 이유가 이것이다.

## 3. 핵심 개념: 상태 추정 경로의 변화

### 3.1 지상로봇 — 두 겹의 안전망

```text
바퀴 인코더 ─┐
             ├─▶ EKF ─▶ odom→base_footprint  (연속적, drift 있음)
IMU ─────────┘
RTAB-Map ──────────────▶ map→odom             (불연속, drift 없음)
```

SLAM이 실패해도 바퀴 오도메트리는 계속 나온다. 위치가 서서히 틀려질 뿐 **로봇은 여전히 "내가 어디쯤 있다"는 추정치를 유지**한다.

### 3.2 드론 — 안전망이 없다

```text
카메라 ─┐
        ├─▶ VIO ─▶ 비행 컨트롤러 EKF2 ─▶ 최종 상태 추정
IMU ────┘                    ▲
                             └─ (실외) GPS
```

**VIO가 실패하면 대체할 것이 IMU 적분밖에 없는데, IMU만으로 위치를 적분하면 수 초 만에 수 미터씩 발산한다.** 실내에서 VIO가 끊기면 드론은 사실상 자기 위치를 모르는 상태가 되며, 이때 위치 제어 모드를 유지하면 위험하다.

이것이 00에서 "VIO가 선택이 아니라 필수"라고 한 말의 구체적 의미다.

### 3.3 비행 컨트롤러가 최종 융합을 담당한다

지상로봇에서는 ROS2 쪽의 `robot_localization` EKF가 융합을 담당했지만, 드론에서는 **비행 컨트롤러 내부의 EKF2가 최종 융합을 수행**한다. ROS2 쪽 VIO는 그 EKF2에 "외부 시각 위치 정보"를 공급하는 입력원 중 하나가 된다.

PX4 기준으로 이 입력을 받을 때 요구되는 조건은 다음과 같다.

| 항목 | 요구사항 |
|---|---|
| 메시지 주기 | **30~50Hz** — 너무 낮으면 EKF2가 융합을 아예 거부한다 |
| 타임스탬프 | VIO 추정 시각과 IMU 시각의 차이를 `EKF2_EV_DELAY`로 보정해야 함 |
| 좌표계 정렬 | VIO 출력 프레임과 EKF2가 기대하는 프레임이 일치해야 함(2.2절 참고) |

## 4. 이 프로젝트에서의 적용 (X3 경험의 이전)

X3에서 쌓은 경험 중 이 문서와 관련해 **그대로 쓰이는 것과 재해석이 필요한 것**을 구분하면 다음과 같다.

| X3 경험 | 드론에서 |
|---|---|
| TF2 좌표계 관리, `static_transform_publisher`로 센서 장착 위치 발행 | **그대로 적용.** 단 `base_footprint` 제거, FLU/NED 변환 주의 |
| `robot_localization` EKF로 휠+IMU 융합 | **재설계.** 융합 주체가 비행 컨트롤러 EKF2로 이동 |
| RTAB-Map의 `map→odom` 발행 | **일반적으로는 아예 안 씀.** 짧은 실내 임무는 VIO(→EKF2)만으로 충분하고, RTAB-Map/loop closure는 "같은 공간을 반복 방문해 지도의 전역 일관성이 필요한" 특수 임무에서만 등장한다(자세한 기준은 [[04_드론에서의_SLAM_백엔드_재평가|드론 적용 - 04. 드론에서의 SLAM 백엔드 재평가]] 3장) |
| D435i IMU 미보정 이슈(01-5, 02-7) | **훨씬 중요해짐.** 자세 제어와 위치 추정 양쪽에 영향 |

## 5. 진단 관점

- **"고도가 이상하다"** → 먼저 FLU/NED 부호 문제를 의심한다(2.2절). z가 정확히 반대 부호로 나온다면 거의 확실히 이 문제다.
- **"EKF2가 VIO를 안 받아들인다"** → `ros2 topic hz`로 VIO 출력 주기가 30Hz 이상인지 먼저 확인한다(3.3절 표). PX4는 주기가 낮으면 조용히 무시한다.
- **"제자리 호버링 중인데 위치가 서서히 흐른다"** → VIO는 살아 있으나 신뢰도가 낮은 상태일 가능성. 저텍스처 환경에서 02-8의 ZUPT 오발동과 유사한 "조용한 실패"가 드론에서도 나타날 수 있다.
- **위치 추정을 신뢰할 수 없을 때는 위치 제어 모드가 아니라 자세 제어 모드로 전환**하는 것이 안전하다 — 05에서 다룬다.
