## 1. 개요

지상로봇에서 "계획이 실패했을 때"를 담당하는 것은 Nav2의 **Behavior Tree와 Recovery 동작**이었다 — 제자리 회전, 후진, 대기, costmap 비우기([[05_Behavior_Tree와_표준_Recovery|Nav2 05]]).

드론에도 같은 계층이 필요하다. **그런데 사는 곳이 다르다.**

> **지상로봇의 복구 로직은 ROS2 안에 있다. 드론의 복구 로직은 대부분 비행 컨트롤러 안에 있다.**

이 차이가 왜 생기는지(2장), 그 체계가 어떻게 생겼는지(3~4장), 그리고 **ROS2 쪽이 무엇을 해야 하고 무엇을 하면 안 되는지**(6장)가 이 문서의 내용이다.

## 2. 핵심 개념: 왜 복구가 FC 안에 있는가

### 2.1 지상로봇과의 구조적 대비

| | 지상로봇 (Nav2) | 드론 (PX4) |
|---|---|---|
| 복구 로직의 위치 | **ROS2**(Behavior Tree) | **비행 컨트롤러** |
| 기본 복구 동작 | 제자리 회전, 후진, 대기, costmap 비우기 | 정지(Hold), 귀환(Return), 착륙(Land), 시동 해제, 비행 종료 |
| "아무것도 안 하기" | **가능하다** — 멈춰 있으면 된다 | **불가능하다** — 가만히 있으려면 계속 제어해야 한다 |
| 복구가 실패하면 | 로봇이 멈춘 채로 있다 | **추락한다** |

### 2.2 두 가지 이유

**① 실패의 대가가 다르다.** 지상로봇은 최악의 경우 멈추면 되지만, 드론은 제어가 끊기는 순간 떨어진다. **복구는 "있으면 좋은 것"이 아니라 마지막 방어선**이다.

**② 복구를 맡길 수 있는 계층이 다르다.** 복구가 필요한 상황은 대개 **위쪽 계층이 못 믿을 상태가 된 상황**이다. 컴패니언 컴퓨터가 죽었거나, SLAM이 무너졌거나, 통신이 끊긴 상황에서 **그 컴패니언 컴퓨터에게 복구를 맡기는 것은 앞뒤가 안 맞는다.**

> **그래서 드론의 복구는 "더 단순하고 더 믿을 수 있는" 아래 계층, 즉 FC에 있다.** [[05_안전과_실전_고려사항|05]] 2장의 계층적 안전 설계가 말하는 바가 이것이다.

### 2.3 결과: ROS2 개발자의 일이 바뀐다

지상로봇에서는 복구 동작을 **직접 만들었다**(Behavior Tree 노드를 짜고 붙였다). 드론에서는 대부분 **설정하고, 방해하지 않는 것**이 일이다.

> **"내가 ROS2에서 안전 로직을 다 짜겠다"는 접근은 드론에서 위험하다.** 짜야 할 것과 맡겨야 할 것의 경계를 아는 것이 이 문서의 실질적 목표다.

## 3. 핵심 개념: failsafe 트리거와 동작

### 3.1 무엇이 failsafe를 부르는가

PX4가 감시하는 실패 조건들이다.

| 트리거 | 대략의 뜻 |
|---|---|
| **배터리** | 잔량 단계별(저/위험/비상) |
| **잔여 비행시간** | 복귀에 필요한 시간이 부족해지는 시점 |
| **조종기(RC) 두절** | 사람이 개입할 수단 상실 |
| **데이터 링크 두절** | 지상국과의 통신 상실 |
| **지오펜스 이탈** | 허용 범위를 벗어남 |
| **위치 추정 상실** | **← 5장에서 따로 다룬다** |
| **Offboard 두절** | **← 컴패니언 컴퓨터가 조용해짐. 위와 다른 실패다** |
| **강풍** | 기체 한계 초과 |
| **기타** | 교통 회피, 낙하산, 원격 ID 등 |

### 3.2 무엇을 하는가 — 심각도 사다리

동작은 **심각도 순서**가 정해져 있다.

```
경고만        →  Hold        →  Return      →  Land       →  시동 해제  →  비행 종료
(로그·알림)     (제자리 정지)   (출발점 귀환)   (제자리 착륙)   (모터 정지)   (최후 수단)
                                                             └─ 공중이면 추락한다
```

**두 가지 규칙이 중요하다.**

**① 여러 개가 동시에 걸리면 더 심각한 쪽이 이긴다.** 예를 들어 RC 두절은 "귀환"으로, 지상국 두절은 "착륙"으로 설정해 뒀는데 둘이 같이 발생하면 → **착륙**이 수행된다.

**② Hold 단계에 유예 시간을 둘 수 있다.** 트리거가 걸린 뒤 곧바로 동작에 들어가지 않고 잠시 제자리에 머무는 설정이 있는데, 이것이 **조종자가 상황을 보고 개입할 창**이 된다. 사람이 있는 비행에서는 매우 유용하다.

> **그리고 언제든 사람이 모드를 바꿔 개입할 수 있다.** failsafe는 사람을 배제하는 장치가 아니라, **사람이 없거나 늦을 때를 위한 장치**다.

### 3.3 통합 상태 기계와, 브라우저에서 돌려보기

PX4는 **v1.14에서 failsafe를 하나의 통합 상태 기계로 재정비**했다. 이전에는 "failsafe가 걸린 중에 다른 failsafe가 또 걸리면?" 같은 상황의 동작이 불분명했는데, 그것이 정리됐다.

> **교육적으로 가장 유용한 것**: PX4는 **실제 기체에서 도는 것과 동일한 failsafe 로직을 브라우저에서 시뮬레이션해볼 수 있는 도구**를 제공한다. 조건을 켜고 끄면서 "이럴 때 무슨 일이 일어나는지"를 **기체 없이** 확인할 수 있다.
>
> 기체 없이 확인할 수 있으므로, 실비행 전 준비 단계에 넣기 좋은 항목이다.

## 4. 핵심 개념: 위치 상실 vs Offboard 상실 — 흔히 혼동되는 두 실패

**이 둘은 완전히 다른 실패이고, 다른 파라미터가 지배하며, 다른 동작을 한다.** 혼동하면 안전 설계 전체가 어긋난다.

| | **위치 추정 상실** | **Offboard 두절** |
|---|---|---|
| 무슨 일인가 | **드론이 자기 위치를 모르게 됨** | **컴패니언 컴퓨터가 명령을 안 보냄** |
| 원인 예 | VIO/LIO 실패, degeneracy, 센서 고장 | ROS2 노드 크래시, 네트워크 끊김, CPU 과부하 |
| 감지 | 추정 오차 한계 초과 또는 무보정 시간 초과 | setpoint 스트림 끊김(일정 시간) |
| 관련 파라미터 | `COM_POS_FS_EPH`, `EKF2_NOAID_TOUT` 등 | `COM_OF_LOSS_T`, **`COM_OBL_RC_ACT`** |
| 드론이 아는가 | **모른다** — 그래서 위험하다 | 안다 — 위치는 아직 멀쩡하다 |

> **`COM_OBL_RC_ACT`는 "Offboard가 끊겼을 때"의 동작이다. 위치 추정이 죽었을 때의 동작이 아니다.** 이름이 헷갈리게 생겨서 자주 오해된다.

**중요한 비대칭이 하나 있다.** Offboard가 끊겼을 때는 **위치 추정이 살아 있으므로 제자리 정지가 가능하다.** 반면 위치 추정이 죽으면 **"제자리"가 어딘지 모르므로 제자리 정지 자체가 불가능하다** — 그래서 대응이 훨씬 거칠어진다(5장).

## 5. 핵심 개념: 위치 추정이 죽으면 무슨 일이 일어나는가

[[01-1_드론의_오도메트리_소스_선택|01-1]] 5장에서 본 강등 사다리를 여기서 자세히 본다.

```
위치 제어 가능 (Position)
      │
      │  ← 위치 추정 상실
      ▼
고도 유지 (Altitude)        고도 추정은 살아 있음 → 높이는 지키되, 수평으로는 흘러간다
      │
      │  ← 고도마저 못 믿음
      ▼
자세 안정화 (Stabilized)     기울기만 잡아준다. 사람이 조종해야 한다
```

**자율 비행 중이고 조종자도 없다면** 여기서 멈추지 않고 **귀환 → 착륙 → 하강**으로 더 내려간다. 최종 수단은 파라미터로 정해진다.

> **핵심 통찰**: **위치 추정 상실의 1차 대응은 착륙이 아니라 "고도 유지로 강등"이다.** 위치는 몰라도 높이는 알면 최소한 떨어지지는 않기 때문이다. 이것이 [[01-1_드론의_오도메트리_소스_선택|01-1]] 3.2절에서 **광류+거리계를 보조로 두라**고 한 이유와 정확히 연결된다 — 그 조합은 **고도와 속도를 지켜주므로, 강등된 상태에서도 드론이 제멋대로 흘러가지 않게** 해준다.

### 5.1 ⚠ 여기도 낡은 정보가 많다

- **`COM_POS_FS_DELAY`는 v1.16에서 제거됐다.** 지연이 고정값으로 바뀌었다. 이 파라미터를 설정하라는 자료는 낡은 것이다.
- v1.14 이전 문서에 나오는 관련 파라미터 이름들도 지금과 다르다.

> **파라미터 이름은 최종적으로 QGroundControl에서 실제 기체를 보고 확인한다.** 문서와 블로그는 버전 기준을 명시하지 않는 경우가 많다. [[01-1_드론의_오도메트리_소스_선택|01-1]] 4.1절의 `EKF2_AID_MASK` 사례와 같은 종류의 함정이다.

## 6. 핵심 개념: ROS2 쪽은 무엇을 하고, 무엇을 하지 말아야 하는가

### 6.1 하지 말아야 할 것 — FC의 안전망을 흉내 내기

**"장애물이 가까우면 ROS2에서 멈추게 하자"**는 발상 자체는 옳다. 실제로 [[03-3_Setpoint_스트리밍과_궤적_추종|03-3]] 7장에서 본 대로 **Offboard 중에는 FC의 회피 기능이 동작하지 않으므로, 회피는 우리 책임**이다.

문제는 그것을 **FC failsafe의 대체물로 여기는 것**이다.

> **ROS2 쪽 안전 로직은 "ROS2가 정상일 때만" 동작한다.** 노드가 죽거나 굶주리면 그 로직도 같이 죽는다. **[[08_사례연구_정지_상태_발산|둠둠 08]]에서 EKF 콜백이 900 ms씩 멈춘 것이 정확히 그런 상황이다** — 그때 ROS2 쪽 회피 로직이 있었어도 같이 멈췄을 것이다.

**그래서 두 계층은 대체재가 아니라 보완재다.** ROS2는 "잘 나는 것"을, FC는 "못 날게 됐을 때"를 맡는다.

### 6.2 해야 할 것

| 할 일 | 왜 |
|---|---|
| **FC failsafe를 실제로 설정하고 검증한다** | 기본값이 우리 임무에 맞는다는 보장이 없다. 특히 실내에서는 **귀환(Return)이 위험할 수 있다** — GPS가 없고 천장이 있다 |
| **강등을 전제로 설계한다** | "위치 추정이 항상 살아 있다"를 전제하지 않는다. 고도 유지로 떨어졌을 때 무슨 일이 일어날지 미리 정한다 |
| **오도메트리 이중화를 검토한다** | [[01-1_드론의_오도메트리_소스_선택\|01-1]] 2.3절. 애초에 강등에 도달하지 않게 하는 것이 최선이다 |
| **노드 응답 없음을 FC가 알게 한다** | 생짜 Offboard의 2 Hz 하트비트는 "노드가 제정신인가"를 증명하지 않는다([[03-3_Setpoint_스트리밍과_궤적_추종\|03-3]] 7.1절) |
| **FC 로그(ulog)를 ROS2 로그와 함께 본다** | "왜 failsafe가 걸렸는가"는 FC만 안다([[05_안전과_실전_고려사항\|05]] 6장) |

### 6.3 실내 비행에서 특히 조심할 것

기본 failsafe 설정은 **실외 GPS 비행**을 상정한 것이 많다.

- **귀환(Return)**은 GPS 좌표 기준으로 홈으로 돌아가는 동작이다. 실내에서는 홈 좌표가 로컬 원점이고, **경로에 벽이 있는지 아무도 확인하지 않는다.**
- **고도 상승 후 귀환**이 기본인 설정도 있는데, **실내에서는 천장이 있다.**

> **즉 실내 자율 비행에서는 failsafe 동작을 "Hold(제자리)" 또는 "Land(즉시 착륙)" 쪽으로 재검토해야 한다.** 기본값을 그대로 두는 것이 가장 위험한 선택일 수 있다.

## 7. 이 프로젝트에서의 적용 (둠둠)

- [[05_정지_회피와_setpoint_처리|둠둠 05]]가 `COM_OBL_RC_ACT`를 `Hold`로 두는 방향을 이미 정해 두었다 — 실내 임무에서 6.3절의 이유로 타당한 선택이다.
- **아직 안 한 것**: 위치 추정 상실 쪽 설정은 검토되지 않았다. 둠둠은 **LIO 하나에 전부를 걸고 있어**([[01-1_드론의_오도메트리_소스_선택|01-1]] 6장) degeneracy 구간에서 곧바로 5장의 강등으로 떨어질 수 있다. **강등 시 무슨 일이 일어나는지를 SITL에서 먼저 확인해야 한다.**
- 3.3절의 failsafe 시뮬레이터를 [[02_빠른_적용_로드맵과_체크리스트|02]] Phase 0에 넣는 것을 권한다 — 기체 없이 할 수 있고, 실비행 전에 반드시 알아야 할 내용이다.

## 8. 진단 관점

| 증상 | 확인 순서 |
|---|---|
| 왜 failsafe가 걸렸는지 모르겠음 | **FC 로그(ulog)를 본다.** ROS2 로그에는 FC 내부 판단이 안 남는다 |
| 설정한 것과 다른 동작을 함 | 여러 트리거가 동시에 걸렸을 수 있다 — **더 심각한 쪽이 이긴다**(3.2절) |
| 튜토리얼의 파라미터가 없음 | 버전 차이(5.1절). QGC에서 실제 기체의 파라미터를 확인 |
| 실내인데 갑자기 상승 후 이동 | **귀환(Return) 동작이 걸린 것.** 실내용으로 재설정 필요(6.3절) |
| ROS2 노드가 멈췄는데 드론이 한참 그대로 감 | 생짜 Offboard의 하트비트는 노드 건강을 증명하지 않는다(6.1절). `COM_OF_LOSS_T`가 지나야 감지된다 |
| 위치를 잃었는데 착륙하지 않고 계속 떠 있음 | **정상이다.** 1차 대응은 고도 유지로 강등이다(5장) |
| Offboard 두절과 위치 상실을 구분 못 하겠음 | 4장 표. 파라미터 계열이 다르다(`COM_OBL_*` vs `COM_POS_FS_*`) |

## 9. 이해도 점검

1. 지상로봇의 복구 동작은 ROS2에, 드론의 복구 동작은 FC에 있다. 왜인가?
2. RC 두절은 "귀환", 데이터 링크 두절은 "착륙"으로 설정했는데 둘이 동시에 발생했다. 무슨 일이 일어나는가?
3. `COM_OBL_RC_ACT`는 어떤 실패에 대한 설정인가?
4. 비행 중 위치 추정이 죽었다. PX4의 1차 대응은 무엇인가? 왜 그것이 합리적인가?
5. 실내 자율 비행에서 failsafe 기본 설정을 그대로 두면 왜 위험할 수 있는가?

> [!info]- 정답 및 해설 보기
> 1. 두 가지 이유다. **① 실패의 대가**: 지상로봇은 멈추면 되지만 드론은 제어가 끊기면 추락한다 — 복구가 마지막 방어선이다. **② 신뢰 계층**: 복구가 필요한 상황은 대개 **위쪽 계층(컴패니언 컴퓨터, SLAM, 통신)이 못 믿을 상태가 된 상황**인데, 그 못 믿을 계층에 복구를 맡기는 것은 앞뒤가 안 맞는다. 그래서 더 단순하고 믿을 수 있는 FC에 둔다.
> 2. **착륙이 수행된다. 더 심각한 동작이 이긴다.** 심각도 순서는 경고 → Hold → Return → Land → 시동 해제 → 비행 종료이고, 여러 트리거가 겹치면 그중 가장 심각한 동작을 한다. "둘 중 먼저 걸린 것"이나 "나중 것"이 아니다.
> 3. **Offboard 두절** — 즉 컴패니언 컴퓨터가 setpoint를 안 보내게 됐을 때의 동작이다. **위치 추정 상실과는 다른 실패**이며, 그쪽은 `COM_POS_FS_*` 계열이 지배한다. 이름이 헷갈리게 생겨 자주 오해되는데, 둘을 혼동하면 안전 설계가 통째로 어긋난다. 결정적 차이는 **Offboard 두절 때는 위치를 아직 알고 있어서 제자리 정지가 가능**하지만, 위치 상실 때는 "제자리"가 어딘지 몰라 그것조차 불가능하다는 점이다.
> 4. **고도 유지(Altitude) 모드로 강등한다.** 착륙이 아니다. 위치는 몰라도 **고도는 알면 최소한 떨어지지는 않기** 때문이다. 수평으로는 흘러가지만 추락은 면한다. 고도마저 못 믿게 되면 자세 안정화로 한 단계 더 내려가고, 자율 비행 중 조종자도 없으면 귀환 → 착륙 → 하강으로 이어진다. 이 구조가 [[01-1_드론의_오도메트리_소스_선택\|01-1]]에서 **광류+거리계를 보조로 두라**고 한 이유와 맞물린다 — 그 조합이 고도와 속도를 지켜주기 때문이다.
> 5. **기본 설정이 실외 GPS 비행을 상정하기 때문이다.** 특히 **귀환(Return)**은 홈 좌표로 돌아가는 동작인데, **경로에 벽이 있는지 아무도 확인하지 않고**, 상승 후 귀환이 기본인 설정에서는 **실내 천장에 부딪힌다.** 실내에서는 Hold(제자리)나 Land(즉시 착륙) 쪽으로 재검토해야 하며, **기본값을 그대로 두는 것이 가장 위험한 선택일 수 있다.**
