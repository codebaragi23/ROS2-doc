# A3. 매핑 품질 진단

> 지도제작 (Part A) 시리즈
> 이전 문서: A2. 매핑 실행 파이프라인과 핵심 파라미터

## 1. 개요

매핑을 마쳤는데 지도가 어긋나 있거나 loop closure가 잘 안 되는 경우, 어디서부터 원인을 찾아야 하는지 정리한다. Part B(Nav2)로 넘어가기 전 마지막 매핑 문서다.

## 2. 핵심 개념: Loop Closure 실패의 3대 원인

1. **센서 동기화 문제** — RGB-D 타임스탬프 불일치로 특징점 매칭 자체가 틀어짐 (A2에서 다룬 `rgbd_sync` 안정성과 직결)
2. **이동 속도 과다** — 특히 회전 시 빠르면 모션 블러로 Visual Odometry가 프레임 추적을 잃음
3. **임계값 미조정** — `Vis/MinInliers`, `Rtabmap/LoopThr`가 실내 조명·텍스처 환경과 맞지 않아 loop closure 자체를 건너뜀

## 3. 이 프로젝트에서의 적용 (Yahboom X3)

과거 진단에서 다음이 확인되었다([[ros2-nav-yahboom]] 참고):

- RealSense 드라이버가 CPU를 과점유하면 `rgbd_sync`의 프레임이 불안정해지고, 이는 곧 위 1번 원인(센서 동기화 문제)으로 이어진다. 즉 파라미터 튜닝 이전에 **드라이버 리소스 사용량 점검**이 우선이다.
- LiDAR 후방 사각지대 문제(각도 파라미터 제한 + 물리적 마운트 위치)가 있었고, 이를 해결해 360도 커버리지를 확보했다. LiDAR 커버리지가 부족하면 ICP 기반 loop closure 후보 자체가 줄어든다.

## 4. 재매핑 체크리스트

순서가 중요하다.

1. **조명 고정** — 형광등 점멸, 자연광 변화를 최소화한다. Loop closure는 조명 변화에 민감하다.
2. **속도 제한** — 회전 시 한 번에 큰 각도로 돌지 않는다 (모션 블러 방지).
3. **경로 설계** — 매핑 시작점 = 종료점이 되도록 경로를 짜서 자연스러운 loop 형성을 유도한다.
4. **겹침 확보** — 새 구역 진입 시 이미 매핑된 영역을 20% 이상 겹쳐서 주행한다.
5. **완료 후 후처리** — `detect_more_loop_closures` 서비스로 놓친 loop closure를 추가 탐색한다.

```bash
# 추가 loop closure 탐색
ros2 service call /rtabmap/detect_more_loop_closures \
  rtabmap_msgs/srv/DetectMoreLoopClosures {}

# 전역 그래프 재최적화
ros2 service call /rtabmap/global_bundle_adjustment \
  rtabmap_msgs/srv/GlobalBundleAdjustment {}
```

## 4-1. 실습: 내가 만든 지도의 그래프를 직접 열어보기

A2 실습에서 만든 `rtabmap.db`를 `rtabmap-databaseViewer`로 열어, **A1에서 개념으로만 배운 "노드와 엣지로 이루어진 그래프"를 실제로 눈으로 확인**한다. 5장의 진단 표는 전부 이 도구를 전제로 하므로, 한 번 열어보지 않으면 표를 읽을 수 없다.

### 준비 사항

* A2 실습에서 생성한 `~/.ros/rtabmap.db`
* 도구 설치 확인: `which rtabmap-databaseViewer` (없다면 `sudo apt install ros-humble-rtabmap`)

### 실행

```bash
rtabmap-databaseViewer ~/.ros/rtabmap.db
```

* 실행 후 상단 메뉴에서 **View → Graph View**와 **View → Constraint View**를 각각 켠다.

### 확인 — 무엇을 봐야 하는가

| 화면 | 무엇이 보이는가 | 어떻게 읽는가 |
|---|---|---|
| **Graph View** | 로봇이 지나간 경로가 점(노드)과 선(엣지)으로 표시됨 | A1 2.5절의 그래프가 이것이다. 경로가 **닫힌 고리를 이루면** loop closure가 성공한 것 |
| **Constraint View** | 엣지 종류별 목록. `Neighbor`(인접)와 `Loop closure`가 구분되어 표시 | **`Loop closure` 엣지가 하나도 없으면** 드리프트를 바로잡을 제약이 전혀 없다는 뜻 |

### 예상 결과

- 정상적으로 한 바퀴를 돌았다면 Graph View의 궤적이 **출발점 부근에서 닫혀 있고**, Constraint View에 loop closure 엣지가 최소 1개 이상 보인다.
- **궤적 끝이 출발점에서 벌어져 있다면** — 누적 드리프트가 보정되지 않은 것이다. 5장 표의 "벽이 어긋나 보임"에 해당한다.
- **같은 복도가 두 겹으로 그려져 있다면** — 같은 장소를 다른 곳으로 인식한 것이다. 5장 표의 "지도가 이중으로 겹침"에 해당한다.

> **이 실습의 의미**: 5장의 증상별 진단표는 "무엇을 보고 판단하는가"를 알아야 쓸 수 있다. 이 도구를 한 번 열어보면 표의 각 행이 화면의 어느 부분을 가리키는지 즉시 연결된다.

## 5. 진단 관점 (증상별)

| 증상 | 의심 원인 | 확인 방법 |
|---|---|---|
| 지도가 이중으로 겹침 | 같은 장소를 다른 노드로 인식 (loop closure 미탐지) | `rtabmap-databaseViewer`의 Graph View로 그래프 확인(4-1절) |
| 벽이 어긋나 보임 | 누적 드리프트가 loop closure로 보정되지 않음 | Constraint View에서 loop closure 엣지 개수 확인(4-1절) |
| 매핑 중 갑자기 위치가 튐 | 잘못된(false positive) loop closure | `RGBD/OptimizeMaxError` 임계값 점검 |
| 특정 구간에서 지도 생성이 멈춤 | ICP 매칭 실패 (특징 없는 벽) 또는 CPU 병목 | `ros2 topic hz`로 처리 주기 측정 |

> **왜 잘못된 loop closure 하나가 지도 전체를 망가뜨리는가**: A1 2.5절에서 다뤘듯, 그래프 최적화는 **모든 엣지의 오차 총합**을 줄이려 한다. 틀린 엣지가 하나 섞이면 최적화는 그 틀린 제약까지 만족시키려고 **주변 노드들을 억지로 끌어당기고**, 결과적으로 멀쩡했던 구간까지 비틀린다. `RGBD/OptimizeMaxError`가 오차가 과도한 엣지를 아예 거부하는 이유가 이것이다.
