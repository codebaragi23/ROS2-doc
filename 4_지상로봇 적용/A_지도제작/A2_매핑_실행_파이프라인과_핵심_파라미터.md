# A2. 매핑 실행 파이프라인과 핵심 파라미터

> 지상로봇 적용 — 지도제작 (Part A) 시리즈
> 이전 문서: A1. RTAB-Map 매핑 원리

## 1. 개요

A1에서 다룬 개념(loop closure, 메모리 관리)이 실제 RTAB-Map 실행 파이프라인에서 어떤 파라미터로 구현되는지 정리한다. 값의 "정답"을 고정하는 문서가 아니라, 각 파라미터가 매핑 결과의 어느 부분에 영향을 주는지 이해하기 위한 참고 자료다. 이 파이프라인이 실제 Yahboom X3의 `map_rtabmap_launch.py`에서 어떻게 구성되는지는 3장 "이 프로젝트에서의 적용"에서 다룬다.

## 2. 핵심 개념: 매핑 파이프라인 구조

```text
RGB-D 이미지 ─▶ rgbd_sync ─▶ Visual Odometry ─┐
                                                ├─▶ rtabmap 노드 ─▶ /map, TF(map→odom)
LiDAR 스캔 ────────────────▶ ICP Odometry ─────┘
```

- **rgbd_sync**: RealSense의 RGB 이미지와 Depth 이미지를 하나의 동기화된 메시지로 묶는다. **LiDAR 스캔은 이 단계를 거치지 않는다** — RGB-D 전용 동기화 노드다. 두 이미지의 타임스탬프가 어긋나면 이후 모든 특징점 매칭이 틀어지므로, 이 동기화 단계가 매핑 품질의 첫 관문이다.
- **Odometry**: Visual(카메라 기반)과 ICP(LiDAR 스캔 매칭 기반) 중 하나 또는 융합된 값을 오도메트리로 사용한다. `Odom/Strategy` 파라미터로 전략을 선택한다.

#### `Odom/Strategy` — 무엇을 기준으로 프레임 간 이동을 계산할 것인가

RTAB-Map의 Visual Odometry는 "지금 프레임을 **무엇과** 비교할 것인가"에 따라 전략이 나뉜다.

| 값 | 이름 | 방식 | 특징 |
|---|---|---|---|
| **0** | **Frame-to-Map (F2M)** | 지금 프레임을 **지금까지 누적한 지역 특징점 지도**와 비교 | RTAB-Map 기본값. 여러 프레임의 정보가 쌓인 지도와 맞추므로 **드리프트가 적고 안정적** |
| **1** | **Frame-to-Frame (F2F)** | 지금 프레임을 **직전 키프레임 한 장**과만 비교 | 가볍고 빠르다. 대신 비교 대상이 한 장뿐이라 **드리프트가 빨리 쌓인다** |

> **선택 기준**: 계산 여유가 있으면 F2M(0)이 거의 항상 낫다. Jetson처럼 자원이 빠듯하고 짧은 구간만 다룬다면 F2F(1)를 고려할 수 있다.

**Visual과 ICP 중 무엇을 쓸 것인가**는 별개의 선택이며, 실행하는 노드(`rgbd_odometry` vs `icp_odometry`)나 `Reg/Strategy`로 결정된다.

| 오도메트리 종류 | 입력 | 강한 환경 | 취약한 환경 |
|---|---|---|---|
| **Visual Odometry** | 카메라(RGB-D) | 무늬·질감이 풍부한 실내 | **흰 벽, 어두운 곳** — 특징점이 안 나옴 |
| **ICP Odometry** | LiDAR 스캔 | 벽·모서리 등 **기하학적 구조**가 뚜렷한 곳 | 긴 직선 복도 — 앞뒤로 미끄러져도 스캔이 똑같아 보임 |
| **융합(Visual + ICP)** | 둘 다 | 서로의 약점을 보완 | 계산 부하 증가, 두 센서의 시간 동기화가 중요해짐 |

A1 2.3절에서 다룬 "ICP는 무늬가 없어도 벽 형태만으로 동작한다"가 바로 이 표의 근거다.
- **rtabmap 노드**: 실제 loop closure 탐색과 그래프 최적화를 수행하는 핵심 노드. A1에서 설명한 WM/STM/LTM 메모리 관리가 이 노드 내부에서 이루어진다.

## 3. 이 프로젝트에서의 적용 (Yahboom X3)

Yahboom X3는 모든 처리(rgbd_sync + rtabmap)를 로봇 본체(Jetson)에서 실행하고, RViz는 호스트 PC에서만 실행하는 구조다([[ros2-nav-yahboom]] 참고). 이 구조에서 실제로 확인된 병목은 **RealSense 드라이버 자체의 CPU 사용량**이었다 — 1280x720x30 해상도에서 CPU 47%를 잡아먹어 `rgbd_sync`가 불안정해졌고, 640x480x15로 낮춰 해결했다.

이 사례가 주는 교훈: RTAB-Map 파라미터를 아무리 잘 튜닝해도, **입력 데이터 자체가 불안정하면(프레임 드롭, 타임스탬프 어긋남) loop closure 품질이 근본적으로 나빠진다.** 파라미터 튜닝은 데이터 파이프라인이 안정된 다음 단계다.

## 3-1. 실습: 실제로 지도 한 바퀴 만들어보기

이 시리즈에서 처음으로 직접 손을 움직이는 단계다. **파라미터 표를 읽기 전에 한 번 돌려보는 것**이 이후 4장을 이해하는 데 결정적이다.

### 실습 목표

매핑을 실행해 `rtabmap.db`를 만들고, 그 안에 loop closure가 실제로 들어갔는지 확인한다.

### 준비 사항

* 센서(RGB-D 카메라, LiDAR)가 연결되어 동작 중 — 응용 05·06편 완료 상태
* 같은 지점으로 되돌아올 수 있는 경로(loop closure를 만들려면 **반드시 출발점으로 돌아와야 한다**)

### 실행

```bash
# 1) 매핑 모드로 RTAB-Map 실행 (기존 DB를 지우고 새로 시작)
ros2 launch rtabmap_launch rtabmap.launch.py \
  rtabmap_args:="--delete_db_on_start" \
  rgb_topic:=/camera/color/image_raw \
  depth_topic:=/camera/depth/image_rect_raw \
  camera_info_topic:=/camera/color/camera_info \
  frame_id:=base_link \
  approx_sync:=true
```

* `--delete_db_on_start`: 이전 지도를 지우고 새로 시작한다. 이것을 빼면 기존 DB에 이어붙는다.
* 토픽 이름은 실제 카메라 드라이버가 발행하는 것과 맞춰야 한다 — `ros2 topic list`로 먼저 확인한다.

```bash
# 2) 별도 터미널에서 로봇을 천천히 주행시킨다
#    - 출발점을 눈에 띄는 곳(특징점이 많은 곳)으로 잡을 것
#    - 한 바퀴 돌아 출발점으로 되돌아온다
```

### 확인

```bash
# 매핑 중 실시간으로 loop closure 발생 여부 관찰
ros2 topic echo /rtabmap/info --field loopClosureId
```

* `0`이 계속 나오면 아직 재방문을 인식하지 못한 것이고, **0이 아닌 숫자가 찍히는 순간이 loop closure가 성공한 순간**이다. A1 2.2절에서 배운 과정이 실제로 일어나는 지점이다.

### 예상 결과

- 출발점으로 되돌아왔을 때 `loopClosureId`에 0이 아닌 값이 찍히고, RViz에서 **지도가 순간적으로 정렬되며 살짝 움직인다** — A1 2.5절에서 배운 "그래프 최적화가 전체를 재조정하는" 장면을 눈으로 보는 순간이다.
- 되돌아왔는데도 계속 0이라면 loop closure 실패다. 이 경우 A3의 진단 절차로 넘어간다 — **실패했다면 그것대로 A3를 읽을 좋은 준비가 된 것이다.**
- 종료 시 `~/.ros/rtabmap.db`가 생성된다. 이 파일을 A3 실습에서 열어본다.

## 4. 관련 파라미터

### 4.1 메모리 관리

| 파라미터 | 기본값 | 튜닝 방향 |
|---|---|---|
| `Mem/STMSize` | 10 | 넓은 환경에서는 늘려 최근 맥락을 더 오래 유지 |
| `Mem/RehearsalSimilarity` | 0.6 | 낮추면 더 다양한 노드를 WM에 보존(재방문 판단이 더 엄격해짐) |

### 4.2 Loop Closure 탐지

| 파라미터 | 기본값 | 튜닝 방향 |
|---|---|---|
| `Vis/MinInliers` | 20 | 실내 저텍스처 환경에서는 낮추는 경우가 많음 (단, 너무 낮추면 오탐 증가) |
| `Vis/FeatureType` | 6 (GFTT/BRIEF, 기본값) | 1(SIFT)이 더 정밀하지만 느림, 2(ORB)가 계산이 가볍고 실내 특징 검출에 유리한 경우가 있음. 전체 대응표는 [[D0-2_특징점_검출_기술자_매칭_비교\|D0-2]] 참고 |
| `Rtabmap/LoopThr` | 0.11 | 값을 낮추면 loop closure를 더 관대하게 인정 |

### 4.3 ICP / LiDAR 스캔 매칭

| 파라미터 | 역할 |
|---|---|
| `Icp/MaxCorrespondenceDistance` | 두 스캔 포인트를 같은 지점으로 볼 최대 거리 |
| `Icp/PointToPlane` | point-to-plane ICP 사용 여부 — 평면이 많은 실내에서 point-to-point보다 정확한 경향 |
| `Icp/Iterations` | ICP 반복 횟수 |

### 4.4 D435i 전용 조정

| 파라미터 | 역할 |
|---|---|
| `Rtabmap/DetectionRate` | 카메라 fps보다 낮게 설정해 처리 부하 절감 (A1 참고) |
| `Imu/Strategy`, `Imu/FilteringStrategy` | D435i 내장 IMU를 오도메트리 예측에 활용할지 결정 |
| `Rtabmap/ImageDecimation` | 이미지 해상도를 낮춰 특징점 매칭 속도 향상 |

> 이 표의 값들은 "정답"이 아니라 조정 방향을 보여주는 참고치다. 실제 값 변경은 재매핑 실험을 통해 검증해야 한다.

## 5. 진단 관점

- `rgbd_sync`가 "Did not receive data since 5 seconds" 경고를 반복한다면 파라미터 이전에 카메라 드라이버 CPU 부하나 네트워크 지연부터 `ros2 topic hz`로 측정해 원인을 좁힌다.
- 매핑 중 로그에 `Odom lost` 계열 메시지가 자주 뜬다면 오도메트리 전략(`Odom/Strategy`) 자체를 의심한다 — 시각적 특징이 부족한 구간(흰 벽, 복도)에서는 Visual Odometry만으로는 취약하다.
