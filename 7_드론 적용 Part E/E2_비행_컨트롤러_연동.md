# E2. 비행 컨트롤러 연동

> 드론 적용 시리즈 · E2
> 이전 문서: [[E1_좌표계와_상태_추정의_차이|E1. 좌표계와 상태 추정의 차이]]
> 선행 학습: [[03_Topic과_Message|ROS2 기초 3편(Topic)]], [[04_Service와_Action|4편(Service·Action)]], [[01_DDS와_QoS_이해하기|응용 1편(DDS/QoS)]]

## 1. 개요

지상로봇에는 없던 계층인 **비행 컨트롤러(Flight Controller, FC)**를 ROS2와 어떻게 연결하는지 다룬다. E1에서 "VIO 결과를 비행 컨트롤러 EKF2에 보낸다"고 한 부분의 실제 구현 방법이다.

## 2. 핵심 개념: 두 개의 컴퓨터

드론에는 성격이 완전히 다른 두 개의 컴퓨터가 함께 실린다.

| | 비행 컨트롤러 (FC) | 컴패니언 컴퓨터 |
|---|---|---|
| 예시 하드웨어 | Pixhawk, Cube | Jetson, Raspberry Pi |
| 실행 소프트웨어 | PX4 또는 ArduPilot (실시간 OS) | Ubuntu + ROS2 |
| 담당 | 자세 안정화, 모터 제어, EKF2 상태 추정, 안전 장치 | SLAM/VIO, 3D 지도, 경로 계획, 미션 로직 |
| 제어 주기 | 초당 수백~수천 회 | 초당 수십 회 |
| 실패 시 | **즉시 추락** | 드론은 계속 떠 있음(FC가 자체 판단) |

**이 분리가 핵심 안전 설계다.** 컴패니언 컴퓨터에서 ROS2 노드가 죽어도 드론은 떨어지지 않는다 — FC가 독립적으로 자세를 유지하며 failsafe 동작(호버링, 귀환, 착륙)을 수행한다. 지상로봇에서 `cmd_vel`을 보내는 노드가 죽으면 그냥 로봇이 멈추던 것과는 안전 구조 자체가 다르다.

## 3. 핵심 개념: 연결 방식 두 가지

### 3.1 uXRCE-DDS (PX4 + ROS2의 권장 방식)

PX4가 ROS2를 위해 만든 네이티브 연결 방식이다.

```text
[FC: PX4]  uXRCE-DDS Client  ──시리얼/UDP──▶  Micro XRCE-DDS Agent  ──DDS──▶  [ROS2 노드들]
                                                (컴패니언 컴퓨터)
```

- PX4 내부의 메시지(uORB 토픽)가 **거의 그대로 ROS2 토픽으로 노출**된다. 별도 변환 계층이 얇아 지연이 적다.
- 응용 1편에서 배운 **DDS를 그대로 쓴다** — 즉 PX4가 ROS2 통신망에 직접 참여하는 형태다.
- 컴패니언 컴퓨터에서 Agent를 실행해야 한다:

```bash
# 컴패니언 컴퓨터에서 Agent 실행 (시리얼 연결 예시)
MicroXRCEAgent serial --dev /dev/ttyUSB0 -b 921600

# 연결되면 PX4 토픽들이 ROS2에 보이기 시작한다
ros2 topic list | grep fmu
```

### 3.2 MAVROS (MAVLink 기반, 레거시·호환용)

MAVLink라는 항공 표준 프로토콜을 ROS 토픽으로 번역해주는 브릿지다.

- ROS1 시절부터 쓰이던 방식으로, **ArduPilot을 쓰거나 구형 FC 하드웨어를 쓸 때는 여전히 이쪽이 현실적인 선택**이다.
- PX4 공식 문서는 플래시 용량이 작은 보드(Pixhawk 2.4.8 등 1MB 보드)에서는 uXRCE-DDS 대신 MAVLink 계열(MAVROS/MAVSDK)을 권장한다.
- 변환 계층이 하나 더 있어 uXRCE-DDS보다 지연이 크지만, 자료와 예제가 훨씬 많다.

### 3.3 어느 것을 고를 것인가

| 상황 | 권장 |
|---|---|
| PX4 + ROS2 Humble + 최신 FC 하드웨어 | **uXRCE-DDS** |
| ArduPilot 사용 | **MAVROS** (또는 ArduPilot의 DDS 지원 확인) |
| 플래시 1MB 구형 보드 | **MAVROS/MAVSDK** |
| 기존 ROS1 자료를 많이 참고해야 하는 상황 | MAVROS (개념 대응이 쉬움) |

## 4. 핵심 개념: Offboard 제어 — ROS2가 드론을 조종하는 방법

ROS2가 계산한 경로를 드론이 따라가게 하려면 **Offboard 모드**를 써야 한다.

**중요한 제약 세 가지**

1. **Offboard 모드로 전환하기 전에 이미 setpoint를 보내고 있어야 한다.** PX4는 목표점 스트림이 살아 있는 것을 확인한 뒤에만 모드 전환을 허용한다.
2. **setpoint를 끊지 말고 계속 보내야 한다.** 일정 시간(PX4 기본 약 0.5초) 이상 끊기면 FC가 **자동으로 failsafe로 전환**한다 — 이는 버그가 아니라 "컴패니언 컴퓨터가 죽었을 때 드론을 지키는" 의도된 안전장치다.
3. **주기적 전송이 곧 생존 신호(heartbeat)다.** 지상로봇에서 `cmd_vel`을 한 번만 보내도 되던 것과 근본적으로 다른 사고방식이 필요하다.

```text
[정상]   ROS2 ──setpoint 20Hz──▶ FC   : Offboard 유지, 목표 추종
[중단]   ROS2 ──✕(0.5초 끊김)──▶ FC   : failsafe 발동 → 호버링/귀환/착륙
```

## 5. 핵심 개념: setpoint의 좌표계와 종류

"setpoint를 보낸다"고만 하면 지상로봇의 `cmd_vel`과 비슷한 것으로 오해하기 쉽다. 실제로는 **완전히 다른 성격의 값**이다.

### 5.1 `cmd_vel`과의 근본적인 차이

| | `cmd_vel` (지상로봇) | setpoint (드론, `TrajectorySetpoint`) |
|---|---|---|
| 의미 | **지금 이 순간** 이 속도로 움직여라 (즉시 명령) | 이 로컬 좌표(또는 속도·가속도)를 **목표로 계속 추종**해라 |
| 기준 | 로봇 바디 프레임, 상대적 | **로컬 NED 프레임의 절대 좌표** |
| 처리 주체 | 모터 드라이버가 값을 그대로 반영 | FC 내부 **캐스케이드 컨트롤러**(위치→속도→추력)가 다단계로 추종 |
| 기억 여부 | 없음 — 매번 새로 계산해 보내야 함 | 없음 — 마찬가지로 스트리밍해야 하지만, 값 자체는 "절대 목표"를 담음 |

### 5.2 position은 "이동량"이 아니라 "좌표"

`TrajectorySetpoint.position = [x, y, z]`를 보내면, 이는 **미터 단위의 절대 좌표**다. "지금 위치에서 x만큼 이동하라"는 상대 명령이 아니라 "**로컬 원점 기준 이 좌표로 가라**"는 절대 명령이다.

```text
예) 원점 기준 (2, 0, -1)에 떠 있는 드론에 position=[5, 3, -1]을 보내면
    → "5m 더 가라"가 아니라 "원점 기준 (5,3,-1)로 가라"
    → 결과적으로 (3, 3, 0)만큼 이동
```

`z`가 NED 프레임이므로 **음수가 위쪽(고도 상승)** 이라는 부호 관례에 주의한다(2.2절).

### 5.3 position/velocity/acceleration을 동시에 줄 수 있다

`TrajectorySetpoint`는 position, velocity, acceleration, yaw를 **한 메시지에 함께** 담을 수 있고, 안 쓰는 필드는 `NaN`으로 비운다.

| 채우는 필드 | 동작 |
|---|---|
| position만 | 위치 제어. velocity/acceleration이 `NaN`이면 FC가 알아서 속도 프로파일을 생성 |
| position + velocity/acceleration | **feed-forward** — 위치 컨트롤러 출력에 velocity를 더하고, 그 결과에 acceleration을 더해 최종 추력을 계산(더 매끄러운 추종) |
| velocity만(position이 `NaN`) | 속도 제어. Nav2의 `cmd_vel`과 개념적으로 가장 가까운 모드 |
| acceleration만 | 가속도 제어 — 저수준 궤적 추종기를 직접 만들 때 씀 |

E3에서 만드는 3D 경로계획기는 보통 **position 또는 position+velocity** 조합으로 setpoint를 채운다.

### 5.4 로컬 원점은 "절대"가 아니라 "이번 비행 한정 기준점"

5.2절의 "절대 좌표"는 **로컬 원점 기준**이라는 전제가 붙는다. 이 원점 자체는 진짜 지리적 절대 위치가 아니다.

- 원점은 **EKF2의 위치 추정이 처음 유효해지는 순간**(대개 arming 시점)의 그 자리로 정해진다. GPS가 없으면 위도·경도와 아무 관계가 없다.
- **GPS가 있으면** arming 시점의 GPS 좌표가 "home position"으로 저장되어, 로컬 원점이 실제 지리좌표와 연결된다.
- 원점은 세션 내내 고정된다는 보장이 없다 — **EKF2가 추정치를 신뢰할 수 없다고 판단하면 원점을 다시 잡는 리셋**이 발생할 수 있고, 이때 로컬 좌표가 순간적으로 점프한다. 이는 [[D1-1_ORB-SLAM3_시스템_개요|D1-1]]·[[D1-3_Multi-Map_System_Atlas와_재추적_병합|D1-3]]에서 반복 관찰된 "active-map IMU reset"과 성격이 같은 현상이다 — ORB-SLAM3가 추정이 불안정해지면 새 맵을 잡듯, EKF2도 추정이 불안정해지면 원점을 다시 잡는다.
- 이 특성 때문에 FC의 로컬 프레임은 지상로봇의 `map`보다는 **`odom`에 훨씬 가깝다** — [[E0_지상로봇과_드론은_무엇이_다른가|E0]] 4-b②에서 "드론에는 map 보정이 대부분 없다"고 한 것이 바로 이 얘기다. GPS나 별도 loop closure로 재보정하지 않는 한, 이 원점은 VIO 드리프트를 따라 서서히 틀어질 수 있다.

## 6. 이 프로젝트에서의 적용 (X3 경험의 이전)

- X3에서는 Nav2가 `/cmd_vel`(속도 명령)을 모터 드라이버에 **단방향으로** 보냈다. 드론에서는 setpoint를 **지속적으로 스트리밍**하고 FC의 상태를 되받아 확인하는 양방향 루프가 된다.
- 응용 1편에서 배운 **QoS가 여기서 결정적으로 중요해진다.** PX4의 uXRCE-DDS 토픽은 `BEST_EFFORT`를 쓰는 경우가 많아, `RELIABLE`로 구독하면 QoS 불일치로 **데이터가 아예 안 들어온다.** 응용 1편에서 다룬 "Topic은 보이는데 echo가 멈춤" 증상이 그대로 재현되는 대표적 사례다.
- Jetson을 컴패니언 컴퓨터로 쓰는 구성은 X3와 동일하므로, D 시리즈에서 확인한 CPU 부하 문제(ORB-SLAM3 96% 등)가 그대로 제약으로 작용한다.

## 7. 진단 관점

| 증상 | 확인 순서 |
|---|---|
| PX4 토픽이 ROS2에 아예 안 보임 | Agent가 실행 중인가 → 시리얼 포트/보드레이트가 맞는가 → `dialout` 그룹 권한(응용 3편과 같은 문제) |
| 토픽은 보이는데 데이터가 없음 | **QoS 불일치를 최우선 의심**(응용 1편) — `ros2 topic echo --qos-reliability best_effort`로 확인 |
| Offboard 모드 전환이 거부됨 | 전환 **전에** setpoint를 이미 보내고 있었는가(4절 제약 1) |
| 비행 중 갑자기 failsafe 발동 | setpoint 스트림이 끊기지 않았는가 → 컴패니언 컴퓨터 CPU 과부하로 발행이 밀렸을 가능성 |
| 고도/방향이 반대로 움직임 | FLU/NED 좌표 변환(E1 2.2절) |
