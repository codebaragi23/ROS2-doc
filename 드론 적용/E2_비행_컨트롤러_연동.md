## 1. 개요

지상로봇에는 없던 계층인 **비행 컨트롤러(Flight Controller, FC)**를 ROS2와 어떻게 연결하는지 다룬다. E1에서 "VIO 결과를 비행 컨트롤러 EKF2에 보낸다"고 한 부분의 실제 구현 방법이다.

## 2. 핵심 개념: 두 개의 컴퓨터

드론에는 성격이 완전히 다른 두 개의 컴퓨터가 함께 실린다.

| | 비행 컨트롤러 (FC) | 컴패니언 컴퓨터 |
|---|---|---|
| 예시 하드웨어 | Pixhawk, Cube | Jetson, Raspberry Pi |
| 실행 소프트웨어 | PX4 또는 ArduPilot (실시간 OS) | Ubuntu + ROS2 |
| 담당 | 자세 안정화, 모터 제어, EKF2 상태 추정, 안전 장치 | SLAM/VIO, 3D 지도, 경로 계획, 미션 로직 |
| 제어 주기 | 초당 수백~수천 회 | 초당 수십 회 |
| 실패 시 | **즉시 추락** | 드론은 계속 떠 있음(FC가 자체 판단) |

**이 분리가 핵심 안전 설계다.** 컴패니언 컴퓨터에서 ROS2 노드가 죽어도 드론은 떨어지지 않는다 — FC가 독립적으로 자세를 유지하며 failsafe 동작(호버링, 귀환, 착륙)을 수행한다. 지상로봇에서 `cmd_vel`을 보내는 노드가 죽으면 그냥 로봇이 멈추던 것과는 안전 구조 자체가 다르다.

## 3. 핵심 개념: 연결 방식 두 가지

### 3.1 uXRCE-DDS (PX4 + ROS2의 권장 방식)

PX4가 ROS2를 위해 만든 네이티브 연결 방식이다.

```text
[FC: PX4]  uXRCE-DDS Client  ──시리얼/UDP──▶  Micro XRCE-DDS Agent  ──DDS──▶  [ROS2 노드들]
                                                (컴패니언 컴퓨터)
```

- PX4 내부의 메시지(uORB 토픽)가 **거의 그대로 ROS2 토픽으로 노출**된다. 별도 변환 계층이 얇아 지연이 적다.
- 응용 3편에서 배운 **DDS를 그대로 쓴다** — 즉 PX4가 ROS2 통신망에 직접 참여하는 형태다.
- 컴패니언 컴퓨터에서 Agent를 실행해야 한다:

```bash
# 컴패니언 컴퓨터에서 Agent 실행 (시리얼 연결 예시)
MicroXRCEAgent serial --dev /dev/ttyUSB0 -b 921600

# 연결되면 PX4 토픽들이 ROS2에 보이기 시작한다
ros2 topic list | grep fmu
```

### 3.2 MAVROS (MAVLink 기반, 레거시·호환용)

MAVLink라는 항공 표준 프로토콜을 ROS 토픽으로 번역해주는 브릿지다.

- ROS1 시절부터 쓰이던 방식으로, **ArduPilot을 쓰거나 구형 FC 하드웨어를 쓸 때는 여전히 이쪽이 현실적인 선택**이다.
- PX4 공식 문서는 플래시 용량이 작은 보드(Pixhawk 2.4.8 등 1MB 보드)에서는 uXRCE-DDS 대신 MAVLink 계열(MAVROS/MAVSDK)을 권장한다.
- 변환 계층이 하나 더 있어 uXRCE-DDS보다 지연이 크지만, 자료와 예제가 훨씬 많다.

### 3.3 어느 것을 고를 것인가

| 상황 | 권장 |
|---|---|
| PX4 + ROS2 Humble + 최신 FC 하드웨어 | **uXRCE-DDS** |
| ArduPilot 사용 | **MAVROS** (또는 ArduPilot의 DDS 지원 확인) |
| 플래시 1MB 구형 보드 | **MAVROS/MAVSDK** |
| 기존 ROS1 자료를 많이 참고해야 하는 상황 | MAVROS (개념 대응이 쉬움) |

## 4. 핵심 개념: Offboard 제어 — ROS2가 드론을 조종하는 방법

ROS2가 계산한 경로를 드론이 따라가게 하려면 **Offboard 모드**를 써야 한다.

**중요한 제약 세 가지**

1. **Offboard 모드로 전환하기 전에 이미 setpoint를 보내고 있어야 한다.** PX4는 목표점 스트림이 살아 있는 것을 확인한 뒤에만 모드 전환을 허용한다.
2. **setpoint를 끊지 말고 계속 보내야 한다.** 일정 시간(PX4 기본 약 0.5초) 이상 끊기면 FC가 **자동으로 failsafe로 전환**한다 — 이는 버그가 아니라 "컴패니언 컴퓨터가 죽었을 때 드론을 지키는" 의도된 안전장치다.
3. **주기적 전송이 곧 생존 신호(heartbeat)다.** 지상로봇에서 `cmd_vel`을 한 번만 보내도 되던 것과 근본적으로 다른 사고방식이 필요하다.

```text
[정상]   ROS2 ──setpoint 20Hz──▶ FC   : Offboard 유지, 목표 추종
[중단]   ROS2 ──✕(0.5초 끊김)──▶ FC   : failsafe 발동 → 호버링/귀환/착륙
```

## 5. 이 프로젝트에서의 적용 (X3 경험의 이전)

- X3에서는 Nav2가 `/cmd_vel`(속도 명령)을 모터 드라이버에 **단방향으로** 보냈다. 드론에서는 setpoint를 **지속적으로 스트리밍**하고 FC의 상태를 되받아 확인하는 양방향 루프가 된다.
- 응용 3편에서 배운 **QoS가 여기서 결정적으로 중요해진다.** PX4의 uXRCE-DDS 토픽은 `BEST_EFFORT`를 쓰는 경우가 많아, `RELIABLE`로 구독하면 QoS 불일치로 **데이터가 아예 안 들어온다.** 응용 3편에서 다룬 "Topic은 보이는데 echo가 멈춤" 증상이 그대로 재현되는 대표적 사례다.
- Jetson을 컴패니언 컴퓨터로 쓰는 구성은 X3와 동일하므로, D 시리즈에서 확인한 CPU 부하 문제(ORB-SLAM3 96% 등)가 그대로 제약으로 작용한다.

## 6. 진단 관점

| 증상 | 확인 순서 |
|---|---|
| PX4 토픽이 ROS2에 아예 안 보임 | Agent가 실행 중인가 → 시리얼 포트/보드레이트가 맞는가 → `dialout` 그룹 권한(응용 6편과 같은 문제) |
| 토픽은 보이는데 데이터가 없음 | **QoS 불일치를 최우선 의심**(응용 3편) — `ros2 topic echo --qos-reliability best_effort`로 확인 |
| Offboard 모드 전환이 거부됨 | 전환 **전에** setpoint를 이미 보내고 있었는가(4절 제약 1) |
| 비행 중 갑자기 failsafe 발동 | setpoint 스트림이 끊기지 않았는가 → 컴패니언 컴퓨터 CPU 과부하로 발행이 밀렸을 가능성 |
| 고도/방향이 반대로 움직임 | FLU/NED 좌표 변환(E1 2.2절) |
